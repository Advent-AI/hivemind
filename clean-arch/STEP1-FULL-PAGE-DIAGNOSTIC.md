# Step 1 full-page source diagnostic — draft

**Status: reviewed for an isolated diagnostic; no prompt change, live send, or adopted source strategy.** The purpose is to find out whether giving Luna the captured page can recover material removed by the historical cleaner without causing it to treat another article, navigation, promotion or a generated summary as the target article. This is a research diagnostic for the isolated clean Step 1 path, not a production acceptance or a replacement for the frozen standard.

## One comparison

Hold the source metadata, open-thesis state, extraction instructions, schema, model setting and limits fixed for each article. Compare the existing cleaned text with the corresponding complete captured `text_page` as the only source-text difference. If an explanation that either input may contain unrelated page material is needed, it must be the same in both arms and audited against the full signed standard and actual schema before use; in that case neither arm is an unchanged production-prompt baseline. Do not claim that such a comparison isolates a particular model instruction or its internal reasoning.

Historical articles can use their recorded actual pre-item thesis states. An independently selected article that has no recorded state must use a separately identified snapshot or an explicitly hypothetical fixed state; do not describe it as historical. The current runner advances state, so an actual comparison needs a separate one-item run per article, arm and draw, or an isolated harness that proves the same fixed context. Verify the built request, including ordered serialization and all metadata, differs only in the intended source text.

The full page is a saved capture, not guaranteed to be the correct or complete original article. Stored title, publisher, URL and dates are available metadata, not proof that all page material came from the intended article. The clean copy and original captured page remain available to the reviewer. Do not silently remove related stories or infer source roles from HTML tags, line length or proximity. Do not silently truncate a page to fit a request.

## What an assessment must expose

- **Recoveries and losses:** whether article 2's CFO outlook and article 16's financing can be read from the full input; relevance and whether either output is useful remain source-backed judgments, not mandatory target labels.
- **Wrong article:** whether the output cites later Firmus recommendations, other Bloomberg stories, the Outlook recommendation cards, or other material not belonging to the target. An incorrect or incomplete captured page must remain visible; identifying it is not equivalent to reconstructing a missing article.
- **Source roles and meaning:** generated-summary labels, attributed facts versus claims, speaker, current plans versus realized facts, qualifications, dates, quotations, and the article-related timeline wrongly removed by the HTML diagnostic. Page headings and structural tags are hints, not automatic role classifications.
- **Pairs and state:** existing-thesis reuse, meaningful new theses with supporting evidence, evidence links, duplicates and noise. A fixed before-state comparison is separate from a sequential forward run; independent arms do not update a shared thesis library.
- **Operational behavior:** request and source sizes, available transport limits, serialization, raw model response, response validation, quotes and errors. Source location is not proof of source identity, attribution or semantic support. The current runner stops on a failed item, and the current production writer accepts one quote; neither limitation is fixed by supplying a whole page.

The current validator changes its additional page check when `source_preparation` is present. The comparison must explicitly apply and report the same location observations against each arm's sent input and against the captured page, without converting unlocated passages into a new hard stop. Missing captures cannot form full-page pairs; inputs that exceed the actual provider limit cannot be compared as complete pages. Count and report these separately rather than silently excluding or truncating them. Retain all refusals, incomplete responses and errors by arm; do not score only the successful answers as if all had completed.

## Evidence already obtained

On the 49 previously saved forward responses, `runner.validate` locates the same 248 of 250 quotations against captured page text as against cleaned text; two remain unlocated. This is an offline compatibility observation on old answers, not an extraction test. Across 6,463 originally fed articles, captured page text has a median 2,015 and maximum 28,516 `o200k_base` tokens, excluding the rest of the request. See [source-loss census](STEP1-SOURCE-LOSS-CENSUS.md) for full distributions, source capture defects, previous selector failures and the HTML candidate's unrelated-story and deleted-context counterexamples.

## Before any model comparison

The complete request and schema must be audited against the signed extraction standard and the clean pair contract, including any identical source-context wording used in both arms. Fix the actual article selection and each original before-state ahead of sending; include known counterexamples and a separately selected, independently source-read set that was not chosen for favorable results. Record any prior exposure. For each article, randomize and interleave repeated clean and full-page requests in the same session; do not pool duplicates or combine output draws into one answer. Independently review the complete responses against the complete sources with condition labels hidden where possible. Report ambiguity, recoveries and regressions per article, including the cases where the input itself is the wrong or incomplete page. Keep any review notes distinct from the frozen gold.

Reviewers may infer a condition from a quotation or content that appears only in one input, so the comparison is condition-hidden where possible, not fully blind. Record cases where the condition is apparent. The proposed sample, request construction, budget, predictions and stop conditions are specified below and have been independently reviewed. The snapshot and schedule still require freezing and the final no-cost preflight before any send. No production input change or quality improvement is implied. The historical system's frozen configuration and corpus remain unchanged.

## Comparison sample

The diagnostic combines nine purposively selected articles from the original 49-item replay (2, 3, 7, 8, 16, 28, 33, 34 and 42) with the eight records selected earlier for the unrelated [date diagnostic](../poc/data/clean-step1-date-unseen-2026-11-07/selection-design.md). Article 33 has the largest captured page by token count among the 49; the others exercise known source-loss, provenance and contamination cases. The second group was previously selected using a fixed seed and source-type strata, but has since been read and used in model calls. Neither group is a fresh held-out test or representative of all sources. The 17 records have captured page text and NVDA ticker tags; their saved request source text and displayed open-thesis state match their saved items and states. The first group's states are the actual recorded before-states; the second group's shared 22-thesis state is explicitly hypothetical. All 17 saved system prompt and schema identities match each other and the current clean draft.

An independent reader additionally verified that all 17 have nonempty clean text, captured pages, NVDA tags, `feed=1`, no copy or superseding marker, and source items matching the saved corpus. The historical states are exploratory and provisional, not verified chronological production state. Rebuilding all 17 control requests with `model.build_request` reproduced their saved order-preserving serialized request objects; for the original 16, replacing a hypothetical page request's source text back with the clean source restored the control object. This does not prove actual HTTP wire bytes or complete the preflight. Article 33 is a known NVIDIA technical article with a generated-summary component, not a test of the longest source in the corpus or of all long-source types.

The 17 × 2 × 3 comparison uses the saved prompt unchanged, varies only source text, randomizes calls and independently reviews every output. The user-facing article replay and separate condition-hidden packets have been exercised with fake responses. This sample is not an acceptance set. A separately suggested BRICS record is not tagged NVDA and cannot be silently assigned to the NVDA test scope. Claude withdrew its suggestion to treat any citation outside the target article as an automatic failure; a cited generated summary or a properly identified comparison requires source-role judgment.

All 17 articles carry July 2026 publication days and October 2026 retrieval timestamps in stored metadata. Page capture can therefore contain subsequent market data, later recommendations and page updates. Source-first notes and output reviews must distinguish the target article, page-generated summary or label, other story, later-dated material, and site material when the page supports those distinctions; uncertainty remains visible. Compare both arms on the same basis and preserve the observed dates. Even an apparent advantage cannot establish how the approach would behave on pages captured near publication.

## Execution contract to review

This table describes an isolated comparison, not a change to the sequential production path. Each scheduled article/arm/draw owns one answer; no comparison answer updates a thesis library or changes another request's before-state. Preserve original publication and capture timestamps as supplied, and use the fixed article state on every read. Never invent event order from wall-clock completion time.

| Situation | Required record or behavior |
|---|---|
| Before dispatch | Save source records, clean and captured text, states, exact request objects, selected IDs and their hashes; derive and record a randomized schedule from a fixed seed. Rebuild controls from saved inputs and show the candidate differs only in `source_item.text`. The fixed existing prompt/schema and metadata are unchanged. |
| Call sent | Record the assigned sequence, article, arm, draw, request, attempt and transport result. Independent completions can arrive in any order; the recorded schedule, not timestamps, identifies them. |
| Complete response | Preserve the raw response and validate it against its own sent text and saved page. Record unresolved links and quote-location observations separately from source identity and meaning. Do not mutate the recorded thesis state. |
| Refusal, incomplete answer or external failure | Preserve the response or error and classify it by attempt and arm. A failed comparison does not silently become an empty answer or disappear from reporting. Follow existing transport behavior; do not treat every failure as a model-quality result. |
| Crash or run ends with work in flight | Distinguish saved terminal results, recorded in-flight requests and unsent schedule entries; do not automatically resend an uncertain call or overwrite an artifact. Any later recovery must use the frozen input and record what was actually sent. |
| Input, configuration or date changes between attempts | Keep the frozen comparison unchanged; a changed request or corrected source is a separately identified comparison, not an invisible resume. Article and capture dates remain those in each saved source, not the current day. |
| Missing page or request too large | Report the item separately; it is not a complete-page pair. Do not silently trim or claim it was compared. These research conditions do not introduce a new stop in the user's normal stream. |
| Review and completion | Independently read each complete answer and its full source; report refusals and missing results, condition leakage, source identity, later material and disagreements. A comparison is a diagnostic result, not a production write or acceptance. |

| Value | Writers and readers to verify before any send |
|---|---|
| Captured page and cleaned text | Saved corpus and trace are read-only inputs; the comparison's request builder and review view read explicit copies. The candidate uses the captured text as sent text and must not silently splice or normalize it. |
| Stored title, publisher, timestamps and entity tags | The saved request sends the title, publisher, publication day, `published_at` and tags in both arms. It does **not** send `retrieved_at`; that timestamp stays in the frozen source record and review materials. These fields do not certify page identity or every passage's date. Adding a capture timestamp to the model input would be a separate intervention. |
| Fixed before-state | Read by the model and link validator; for original replay cases it is the saved exploratory state, and for the other cases it is the explicitly hypothetical snapshot. No arm writes it. |
| Raw response and interpreted evidence | The comparison record, source reviewer and replay view read the response; the existing validator reads each arm's sent text and page. The production writer is not exercised and its single-quote limitation remains open. |
| Source-location status | The validator and replay reader expose original model text and any located slice; location, source role, passage support and thesis relevance remain separate observations. |

The new path must also be checked against every existing clean-runner validation, including schema, local identities, links, original-page citation handling and the behavior of unanswered or refused calls. The existing `scripts/preflight.py` runs the historical checks it names; it is not assumed to exercise this comparison path. The full request and any added instruction must be reviewed against the frozen standard. Nothing in this draft changes D199's one-call rule, the frozen prompt or the source corpus.

## Proposed execution details

- Freeze the 17 source records, original saved request objects, source page and clean text, and before-states as a separate snapshot with SHA-256 hashes. Record cohort identity and the research notes; do not mutate the saved databases or reuse a historical response as a fresh result.
- For each record and each of three draws, send one unchanged saved clean request and one copy with only `source_item.text` replaced by the captured `text_page`. Keep identical system prompt, schema, model, settings, metadata, tags and thesis context. Verify the exact control request against the model builder, and verify that substituting the original text back into the page request restores the same order-preserving serialized request. Construct the full schedule with seed `7631107` and preserve it before the first send.
- Reuse the existing `LiveTransport`, `model.openai_transport`, clean validator and per-attempt trace pattern used in the previous date diagnostic. Before using a live transport, verify with a fake HTTP receiver that the request body bytes match the hash of `json.dumps(request).encode('utf-8')`, which the actual transport sends. Preserve each response or failure; do not blindly retry a call whose outcome is unknown. Do not advance a thesis state.
- Adapt rather than copy the date diagnostic's assumptions: its validator passes the original clean item to both arms and its reviewer packet represents a shared source input. For this comparison, validate each answer against the exact text sent in that arm, and separately report captured-page location for both. Preserve each arm's actual input in the audit record; review packets must not falsely say the inputs are the same. Condition labels can be hidden, but page-only quotations can reveal them. The validator must not stop the run solely because a quote does not locate.
- A preliminary calculation using the existing transport's conservative reservation formula and rates of $0.50 per million estimated input tokens and $1 per million maximum output tokens is approximately **$4.89 reserved for 102 calls**, before any drift in request bytes or settings. This is a budget reservation, not a bill or a quality measure. The comparison's proposed maximum reservation is $6, with a 90-minute overall limit and at most eight workers as in the prior diagnostic. Verify exact values from the frozen schedule; record provider usage and actual charges if available. No production or permanent source database is written.
- Before any live request, run the historical `scripts/preflight.py`, read skipped/refused cases and failures, and perform an independent clean-path preflight on the 17 request pairs, saved answer/schema checks and equal source/page location observations. Use positive and mutated negative controls for request identity and the body-byte assertion. Report exactly what each check covers; the historical preflight does not establish this diagnostic's source or semantic quality.
- Have independent readers record source observations before the new outputs; see [source-first notes](STEP1-FULL-PAGE-SOURCE-NOTES.md). After sending, review every complete answer with condition labels hidden where possible, and report every refusal, incomplete answer and unsent attempt. Do not demand a fixed fact count, treat a page location as an automatic failure, or combine the historical and hypothetical-state groups into a population accuracy estimate. A comparison of particular source-backed recoveries or regressions is not proof of why the model made them.

Predictions to check, rather than acceptance thresholds: the whole page makes the two previously removed source passages available; the same page can expose related stories and generated summaries; source text and output token usage can increase; and the model may either preserve or confuse source roles. A favorable or unfavorable outcome on these selected inputs remains diagnostic. An independent reader reviewed the source selection, execution contract, offline harness, review artifacts and failure handling; findings were corrected and the fake-transport checks passed. The snapshot and schedule are frozen separately immediately before execution.

The aggregate reservation must be owned by one serialized coordinator even if calls run concurrently; the prior probe's separate per-call transports do not provide a shared budget. Reserve against each frozen request before dispatch, persist that reservation with its schedule ID, and never dispatch the same scheduled attempt twice. A schedule entry is initially queued, then recorded as dispatch-started before the transport call, then complete or failed with its response/error. After a crash, dispatch-started without a terminal record means the outcome is unknown: preserve it and do not automatically resend. A source-specific bad response or validation failure is recorded for that entry; do not turn it into a content-based stop for the rest. A missing credential, global authentication rejection, elapsed run budget or inability to preserve the audit record stops dispatch and leaves remaining entries explicitly unsent. Exact handling of provider-wide failures and recoverability needs to be reconciled with the real transport and independently reviewed before freezing the schedule.

For this isolated diagnostic, the proposed handling follows the existing single-attempt transport: HTTP 400 is recorded for the affected request, including a provider size rejection; other independently scheduled requests may proceed. HTTP 401/403 or a shared endpoint/model 404 stops new dispatch because the same credential or endpoint is used across the comparison. HTTP 429 or 5xx is recorded for that attempt without an automatic retry; other already scheduled work may proceed within the frozen budget and deadline. A malformed body, refusal, incomplete response or schema failure is preserved as a failed attempt and does not become an empty answer. A timeout or lost connection is recorded as an uncertain outcome because the provider may have received the request; it is not automatically resent. If an audit write fails, stop dispatch and drain already in-flight attempts as far as their results can be recorded; list entries with uncertain or missing terminal records and all unsent entries. On global stops, already-dispatched work is allowed to finish and is recorded rather than silently cancelled. These are comparison-run controls, not new source-content gates on the user's stream.

The native validator first locates a quotation in the sent text and, for a prepared item, checks that located slice literally against `text_page`. That is not an independent page lookup. The review record must preserve the native result and also perform separate location observations against the sent text and captured page using the existing lookup behavior, preserving raw quotes and each located slice or ambiguity. Those independent observations are diagnostic and must not modify the stored model answer or automatically reject a pair.

The existing lookup returns `None` for both a missing match and multiple distinct candidate slices, and an exact matching value can occur more than once. Unless a separate position-aware method has been designed and verified, display the result as **unresolved** rather than asserting a particular reason or a unique source position.

An initial [historical preflight](../poc/data/clean-step1-source-loss-census-2026-11-07/historical-preflight.txt) replayed 243 archived extraction answers. It reported the previously documented two schema refusals, seven quote refusals, five same-quote merges and two skipped matching records. It does not exercise this proposed clean comparison or its source semantics. The final pre-send check must confirm the actual frozen inputs and account for any difference; this initial run is not a claim that all checks or source quality passed.

The exploratory harness's offline control also replayed the 48 previously saved date-diagnostic answers: it inspected 296 passage instances and saw one changed location value between clean text and the captured page. In that Ising example, the clean text joins passages across intervening checkpoint-name lines, so the quotation appears contiguous in clean text but is unresolved on the captured page. The model was not called for this check. The difference is an observation about source continuity, not a reason to discard the evidence automatically.
