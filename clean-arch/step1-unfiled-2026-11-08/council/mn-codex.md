**Version 1 is not ready for implementation or a paid run.** The proposed changes are a reasonable starting point, but the design does not yet prove that the fresh path preserves behavior, enforce one ceiling across every paid call, or specify enough reading to support the claims it proposes.

### Serious findings

1. **The proposed parameters are close to the smallest change, but they are incomplete.** Reusing the existing case builder, ladder runner and adapter is preferable to building a second pipeline. However, the adapter also reads the ladder **archive** to obtain the configuration checksum and restricts live output to its existing output root. Those inputs and the output authorization must follow the fresh run too; changing only the four listed arguments is insufficient. The case builder also currently combines a stored census packet with a separate acceptance trace and requires exactly 44 cases. Its fresh-input path must preserve the old default while checking the actual set of opened theses, unique draw-qualified IDs and opening articles. [Case builder](/Users/lchingen/hivemind/clean-arch/step4-2026-11-10/stage_a/build_cases.py), [adapter](/Users/lchingen/hivemind/clean-arch/step4-2026-11-10/stage_b/ladder_adapter.py).

   The shared-budget wiring is additional behavior, not just parameterization. The design should identify its entry points without modifying frozen Step 2 code.

2. **The proposed $0 proof is necessary but does not yet show that wiring changes nothing.** The stored case and database comparisons test useful outcomes, but they omit the launcher, the fresh named-input route, request bytes, spending wrappers and failure paths. Add deterministic checks that:

   - Compare the actual requests sent, including key order and Step 1’s provider adaptation, against the existing path; replay stored answers and compare outcomes by case and pass, not concurrent file order.
   - Exercise both defaults and explicit fresh paths, including the ladder archive checksum, output location and segmented trace. Wrong trace, case, ladder and archive inputs must each be detected; an unexercised mutant is not a pass.
   - Compare all relevant database rows **and** counts, links, refusals and incomplete outcomes, with row ordering and incidental file metadata handled explicitly.
   - Exercise the shared ceiling with fake services, concurrent sends, retries, missing usage, overrun and crash-held reservations. Show that every paid entry point is intercepted.

   No such proof has been run in this review. A match on stored outputs alone would not establish that fresh calls use the same requests or that spending is bounded.

3. **The shared ceiling needs a concrete mechanism before a slice.** I recommend one ledger for the slice, all six full draws, retries and any paid reader calls, with a fixed slice sub-limit and a fixed total limit inside D439’s remaining $40. Determine the remaining balance from the current recorded spend before setting a number; the design’s roughly $9 is an estimate, not a ceiling.

   - **Step 1:** retain `LiveTransport`’s provider adaptation, supported-model checks, elapsed-time limit, call limit and single-attempt behavior. Replace its cumulative-dollar accounting with a reservation on the shared ledger for **each actual attempt**, settling from valid usage and charging the reservation when usage is unavailable. Do not wrap it in the production transport’s separate retry loop: that would change retry behavior. [Live transport](/Users/lchingen/hivemind/clean-arch/step1/live.py), [shared ledger](/Users/lchingen/hivemind/clean-arch/e2e-comparison-2026-11-13/budget_replay.py).
   - **Embeddings:** instrument the existing embedding call at its external boundary without changing frozen search behavior. Reserve a conservative bound for each of its up to three attempts **before** the call, settle valid token usage, and retain the bound for failed or unknown-usage attempts. A dry run can count the actual texts after Step 1; use a documented conservative token bound and the configured embedding price, then refuse before sending if it cannot be bounded. A slice measures cost but does not itself enforce a ceiling. The helper currently retries internally, so an outer wrapper that reserves for only one attempt is inadequate. [Embedding helper](/Users/lchingen/hivemind/src/hivemind/search.py:55), [forward runner](/Users/lchingen/hivemind/clean-arch/step2/run_forward.py:92).
   - Apply the same accounting to Jev, ladder, judge, production and paid readers. Preserve each component’s existing retry and stop semantics; avoid charging the same attempt twice. The present ledger can flag an actual charge above its reservation only **after** it occurs, so document that this is an enforced reservation ceiling with possible overrun if a bound is wrong, and test the stop of all subsequent sends. A refused reservation must stop the whole run, not merely mark one item failed and continue.

4. **“What the run can decide” is incomplete.** I agree with the all-23 census, seven graded separately, two-family matching, unresolved counts and tracing losses. The run can describe this sample and locate failures; it cannot establish production superiority or D427 acceptance. It also cannot declare Stage A covered merely because there are three sends: the independent readings, complete denominators and applicable lines must be exercised.

   Stage B needs all five lines specified, including completed draws, the share of laddered theses judged, the eight eligible controls with the material shown, and both comparisons with the stored baseline. Its reading rules also require at least 30 decided judgments, both readers’ verdicts on each thesis’s last judgment, nonzero denominators and no more than one-third disputed verdicts. Otherwise the affected result is **not measured**. The prior protocol samples when judgments exceed 400; the version 1 statement that every judgment must always be read is too broad. [Stage B protocol](/Users/lchingen/hivemind/clean-arch/step4-2026-11-10/DESIGN.md:1436).

   “Stored Step 2 checks are reported” is ambiguous: old results do not check new draws. Run and report the existing checks on each fresh draw, including refusals, pending links and unresolved Step 1 links; identify any quality checks that the fresh run does not exercise. [Forward runner](/Users/lchingen/hivemind/clean-arch/step2/run_forward.py:125).

5. **The failure and timing contract is still open.** Write the state-by-event table before coding. At minimum it must distinguish a valid “no ladder” from twice-refused or missing outcomes; account for links to unjudged theses; stop on missing or mismatched cases; preserve opening-day ordering and the due-day guard; and define incomplete Step 1 or Step 2 output. For the judge, the existing rule allows one new-folder redo only for specified answer or transport failures; a crash is recorded and never resumed, while an unfinished redo stops the run. A budget stop must stop every component and leave outstanding reservations counted. The proposed table must also cover a crash between a send and recording its charge. [Stage B runner](/Users/lchingen/hivemind/clean-arch/step4-2026-11-10/stage_b/run_stage_b.py:45).

### Answers to the open points

- **Shared ceiling:** use the single ledger and per-attempt interception described above. Set the actual limits only after checking D439’s remaining balance and the conservative bounds; include reader costs and the slice. Test enforcement at $0 before any send.
- **Reading workload:** commit to the existing Stage A and Stage B reading procedures if the purpose includes reporting their lines. Stage A’s stored estimate was about 35 minutes per reader for 132 answers, plus disputes; Stage B estimated 13–18 total reader-hours for 210–360 judgments, including the other specified work. These are historical estimates, not a promise for fresh draws. Before sending, budget the readers and their paid calls, plant the required controls, and specify who reads disputes and every unsupported judgment. If that work cannot be funded or staffed, narrow the run to the census and mark the affected lines unmeasured; do not imply that three sends alone covered them.
- **Slice:** yes. Run one fresh clean day through all steps, including ladder and judge, with its own sub-limit inside the shared total. Review requests, outputs, links, timing, spending and failures before deciding whether to launch the full same-day comparison. The slice is a wiring check, not one of the three full draws or evidence of quality.
- **State table:** adopt the existing Stage B redo rules exactly for the judge, and explicitly specify the other components as above. Do not assume the judge’s retry rules automatically apply to Step 1, embeddings or ladder generation.
