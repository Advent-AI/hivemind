### 2. Can an ordinary case exceed $2?

For the **specified launcher**, I found no ordinary overlap, redo, judge-thread or intact-ledger crash path that double-spends the same recorded balance. The launcher lock excludes a second launcher; judge threads reserve under one lock; and a later process counts an unfinished call at its saved reservation. [Launcher](/Users/lchingen/hivemind/clean-arch/step4-2026-11-10/stage_b/run_stage_b.py:38), [reservation](/Users/lchingen/hivemind/clean-arch/step4-2026-11-10/stage_b/ladder_adapter.py:67), [ledger total](/Users/lchingen/hivemind/clean-arch/step4-2026-11-10/stage_b/ladder_adapter.py:101)

That conclusion has a boundary: the hard cap assumes the calculated reservation covers what the provider bills. The code estimates input tokens from request bytes and uses the output cap; it does not enforce that returned usage stays within the reservation. I found no evidence here that the ordinary requests exceed it, but the code alone does not prove an unconditional billing cap. [Estimate](/Users/lchingen/hivemind/clean-arch/e2e-2026-11-09/budget.py:30), [actual charge](/Users/lchingen/hivemind/clean-arch/step4-2026-11-10/stage_b/ladder_adapter.py:84)

The cap-stop restart defect does **not**, by itself, show spending past $2: the reconstructed limit still applies. It does violate the separate instruction that a cap stop ends the whole send.

### 3. Other material departures

- **A draw with zero judgements can be reported complete.** The design explicitly calls such a draw incomplete. The launcher instead records `complete` whenever `replay` returns, without checking the judgement count. The reported dry runs all had judgements, so this is a failure-path defect rather than evidence that the current inputs will produce an empty draw. [Design](/Users/lchingen/hivemind/clean-arch/step4-2026-11-10/DESIGN.md:1485), [launcher](/Users/lchingen/hivemind/clean-arch/step4-2026-11-10/stage_b/run_stage_b.py:83)
- **A crash leaves an ambiguous restart.** A later launch skips an existing draw folder and can start its redo without a recorded reason for the first stop. The design says a crash stops the replay and a new replay is launched deliberately; the plan limits automatic redo to identified, changeable failures. [Design](/Users/lchingen/hivemind/clean-arch/step4-2026-11-10/DESIGN.md:986), [folder handling](/Users/lchingen/hivemind/clean-arch/step4-2026-11-10/stage_b/run_stage_b.py:59)
- The main replay otherwise follows the reviewed path: it places the stored first-send ladder before the opening article’s evidence, commits the day’s writes, and calls the unchanged judge. Stage A **has not passed**; Stage B measures the judge on those known-faulty ladders, as D429 allows. [Replay](/Users/lchingen/hivemind/clean-arch/step4-2026-11-10/stage_b/ladder_adapter.py:252), [D429](/Users/lchingen/hivemind/docs/DECISIONS-log.md:4771)
