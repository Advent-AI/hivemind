我建议采用：**关系数据库保存原始记录和历次判断；同对象的观点全部拿来比较；跨对象找证据去向时按需使用混合检索；所有合并、挂载、修订和重判都留下记录。**

Embedding 有用，但它主要回答“哪些值得拿来比较”，不能决定“是不是同一个观点”。

我已读完 [重建记录，尤其第 9、10 步和“合成”](/Users/lchingen/hivemind/docs/views-rebuild-log.md)，也核对了相关决策。以下保留已经定下的单层观点结构，不恢复被撤回的“长期观点＋多期考卷”。没有修改文件。文中的 NVDA、H20、利率例子均用于说明机制，不代表对具体公告或走势的判断。

## 1. 三个问题分别怎么做

### 1.1 去重：先明确“同一个”是什么，再选择匹配技术

**现实里别人怎么做**

实体解析（entity resolution）是把不同写法的记录认成同一个现实对象。通常分两步：

- **Blocking，缩小比较范围**：先按名称、类别、标识符或相似度找候选，避免所有记录两两比较。
- **Matching，确认身份**：再检查候选是否真的指向同一个东西。

《Match, Compare, or Select?》比较了三种大模型问法：

| 问法 | 模型做什么 | 对你们的启发 |
|---|---|---|
| Match | 两条记录是不是同一个 | 适合独立核对，但看不到其他相近候选 |
| Compare | 两个候选中，哪个更像目标 | 能排序，“更像”不等于“相同” |
| Select | 从一小组候选中选出对应项 | 适合一个对象只有两三条观点的情况 |

论文发现，让模型同时看到候选之间的差异有帮助，但也存在候选位置偏差，以及“实际上没有匹配项”的问题。这项研究针对商品、论文、影视记录，不能直接当作金融观点匹配的准确率保证。[论文](https://arxiv.org/html/2405.16884v1)

预测平台则提醒我们：**问题的身份不能只看标题。** Metaculus 要求问题正文、判定条件、单位和时间一致；Polymarket 也明确区分市场标题与真正决定结算的规则。[Metaculus 出题指南](https://www.metaculus.com/question-writing/)、[Polymarket 规则说明](https://help.polymarket.com/en/articles/13364548-how-are-markets-clarified)

我没有找到足够的一手资料，证明这些预测平台在生产中采用了某种自动去重算法；不能据此宣称它们“也是用 embedding 合并问题”。

**在你们这里，推荐这样做**

第一步直接沿用已定设计：**按对象 ID，取出这个对象全部开着的观点。**

只有两三条时，检索没有必要提前筛掉其中任何一条。模型一次看全，比“先向量检索取第一名，再问是不是同一个”更容易分辨相邻问题。

但“看的是什么”需要有一份简短、明确的描述，不能只有标题：

| 内容 | 用途 | 例子 |
|---|---|---|
| 对象 ID | 确认挂在哪个研究对象上 | NVDA；主题“芯片出口管制” |
| 数字还是事件 | 区分问题类型 | 收入同比；许可执行状态 |
| 看哪个数／哪件事 | 身份的核心 | 中国区数据中心收入；H20 对华出口许可 |
| 范围和口径 | 区分相近但不同的问题 | 中国区与全球；数据中心与全部业务 |
| 统计方式／事件阶段 | 防止混淆 | 收入额与同比；宣布与实际发证 |
| 目标期间、到期日、梯子 | 保留既有观点的考题 | 不因新候选而修改 |

这只是把已有的“看的是什么”写清楚，**不需要另建一个永久存在的观点父层**。

模型的匹配结果应允许三种情况：

1. **同一个**：选已有观点 ID，说明对应的口径；只挂证据。
2. **不同**：说明决定性的区别，作为新观点候选。
3. **说不清**：缺少范围、口径或对象信息，交现有复核路径，不强行选一个。

候选的方向、到期日、梯子都不能成为“不同观点”的理由。尤其不能把看多与看空的两个说法建成两条观点——它们可能正是在回答同一个问题。

确认身份后，数据库负责守住“同一身份同时只有一条开放观点”。PostgreSQL 可以用只约束开放记录的唯一索引实现这一点；但前提是模型已经把同义表达归到同一个身份键。**唯一索引不能替你识别同义词。**[PostgreSQL 部分唯一索引](https://www.postgresql.org/docs/current/indexes-partial.html)

**会在哪里出错**

- **过度合并**：“H20 对华许可”和“Blackwell 对华许可”高度相似，却可能反向变化，必须分开。
- **合并不足**：“H20 export licensing to China”和“H20 对华出口许可执行情况”可能是同一个。
- **范围不明**：“中国业务恢复”未必等于“中国区数据中心收入恢复”。不能因为前者更宽泛就直接吞并。
- **日期误用**：按你们的规则，另一个期限的同口径候选仍合入已有观点。但候选附带的下一财年数字，不能因此变成本财年观点的答案。

最后一种意味着：**你们主动选择不同时跟踪同一口径的多个期限。** 这是产品约束，检索系统不应偷偷把日期加回身份键。

另外，去重只能防止同一个问题问两遍，不能阻止模型提出二十七个不同的小问题。“什么值得占用每个对象的两三条观点”仍是独立的投研选择，不能用相似度阈值代替。

### 1.2 纳入证据：这是多对多的关联问题，不是第二次去重

**现实里别人怎么做**

事实核查中的 claim matching，是拿一条新说法去找已经核查过、可能有帮助的说法。CLEF CheckThat! 将它设计成排序任务，参与系统采用过词语匹配、句向量和重排等方法。[CheckThat! 2022 任务报告](https://ceur-ws.org/Vol-3180/paper-29.pdf)

这里有一个关键区别：

> 找到“有关联的旧说法”，不等于确认“两个说法完全相同”；也不等于确认“这条证据支持旧说法”。

这正好对应你们的两个问题：去重判断身份，挂证据判断关联。

常用的检索组合是：

- **BM25**：根据词语重合及其稀有程度排序，擅长找 H20、MI308、公司名这类明确词。
- **向量检索**：把文本变成表示语义的数字向量，擅长跨措辞寻找相关内容。
- **RRF**：按各检索结果的名次合并列表，避免直接相加两种不可比的分数。

这是成熟的混合检索思路，但 RRF 并非在所有数据上最优；已有研究发现，经过调节的分数加权可以优于 RRF。因此它适合作为简单起点，不是无需验证的标准答案。[RRF 原论文](https://cormack.uwaterloo.ca/cormacksigir09-rrf.pdf)、[混合检索融合方法研究](https://arxiv.org/abs/2210.11934)

**在你们这里，推荐三条找去向的路径**

**第一条：明确对象，直接取全。**

证据已经明确涉及 NVDA，就检查 NVDA 开着的全部观点。不要只沿着抽取模型提出的那个候选观点挂载：同一份文件可能提出错问题，却提供了有价值的证据。

**第二条：明确主题或其他对象，补充相应观点。**

AMD 的文件可以包含 H20／MI308 所属政策范围的证据。这里文件发行人是 AMD，证据说的事情却属于出口管制主题。

因此：

- 文件来自谁，是出处信息。
- 证据说的是谁、什么事，是关联信息。
- 最后挂到哪个观点，是观点库的决定。

三者不能共用一个“对象”字段。

**第三条：还有未覆盖的关联，再做跨对象检索。**

检索对象是全库开放观点的“问题＋范围＋口径＋事件阶段”，查询内容是证据及理解它所必需的上下文。可以把关键词与向量结果合并，再让模型逐条判断是否存在直接关联。

**每条证据允许命中零条、一条或多条观点。** 去重可以用单选，挂证据不能强制单选。

重排是否值得加，可按这个顺序考虑：

| 方法 | 适合做什么 | 此时是否必要 |
|---|---|---|
| 同对象全部比较 | 两三条观点中找关联 | 必要，而且简单 |
| BM25＋向量 | 跨对象、跨语言找候选 | 有明确漏召回时加入 |
| Cross-encoder | 同时读取证据和候选观点，对相关性重新打分 | 候选较多时考虑 |
| 大模型判断 | 解释具体关联、区别直接证据与背景 | 小候选集上适用 |

Cross-encoder 是把两段文本放在一起读的模型，比各自算向量更能比较细节，但逐对处理更费计算。它仍然主要输出相关性，不自动拥有你们的观点身份规则。[Sentence Transformers 检索与重排文档](https://sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)

**直接证据与依赖必须分清**

假设一份 FOMC 声明只公布政策利率决定：

- 证据挂到美联储利率观点。
- 利率观点换格后，通知依赖它的 ETH、JPM 等观点。
- 不把这句话自动复制成每家公司的直接证据。

假设另一份文件同时说明政策变化，以及 NVDA 因此确认的收入影响：

- 政策那句话可以挂政策观点。
- 收入影响那句话可以挂 NVDA 观点。
- 如果确实是同一句话直接包含两个判断所需的信息，也可以共享同一个证据 ID，建两条连线。

**跨对象检索扩大的是“需要检查的范围”，不是自动产生因果关系。**

**中英文混合时，怎么处理**

建议同时保留：

- 原文；
- 已知对象的中英文别名；
- 产品型号、证券代码等精确字符串；
- 用于检索的规范化描述。

中文分词和跨语言语义是两个问题。支持中英混排的分词器能改善词语检索，却不会自然知道“英伟达”和“NVIDIA”是同一对象。多语言向量模型可以补跨语言召回，例如 BGE-M3，但仍须用你们的中英金融样本验证。[Elastic 中文分析器](https://www.elastic.co/docs/reference/elasticsearch/plugins/analysis-smartcn)、[BGE-M3 论文](https://arxiv.org/abs/2402.03216)

翻译可以作为检索辅助，不能替换原文出处。`H20`、`H200`、`Blackwell` 也不能因为语言规范化而被揉成同一类。

**证据“只存一次”，需要区分三件事**

| 情况 | 推荐处理 |
|---|---|
| 同一来源版本、同一位置，被重复抽取 | 复用同一证据，记录抽取出处 |
| 多家媒体转述同一条独家 | 保留各自出处，记录共同原始来源；不当作多次独立确认 |
| 不同来源独立确认同一事实 | 分别保留；相同内容不代表相同身份 |

不能仅凭句子相似就删掉证据。否则既可能丢掉独立确认，也可能把二十篇转载当成二十条新证据。

挂载阶段只确认“相关”。**往哪边推仍由你们已定的重判调用写在连线上**，无需再造一套方向判断。

### 1.3 演进与血缘：保留当时的输入、决定和输出，而不只是历史文本

**现实里别人怎么做**

这里值得借鉴的是机制，而不是直接采用某个记忆产品的数据模型。

| 方向 | 值得借鉴 | 不能照搬的地方 |
|---|---|---|
| Mem0 2025 年论文 | 抽取后检索旧记忆，再决定 ADD／UPDATE／DELETE／NOOP | 反驳旧说法不意味着应该删除旧证据 |
| Mem0 当前新算法 | 官方迁移文档改为只追加，变化的信息并存，检索时处理相关性 | 保留历史不等于已经保存每次投研判断的完整输入 |
| Graphiti／Zep | 原始输入与派生关系相连；保存时间范围、去重和失效信息 | 不能把“后到的说法”普遍当作更正确的说法 |

来源：[Mem0 论文](https://arxiv.org/html/2504.19413v1)、[Mem0 官方迁移文档](https://github.com/mem0ai/mem0/blob/main/docs/migration/platform-v2-to-v3.mdx)、[Graphiti 项目](https://github.com/getzep/graphiti)。

尤其值得注意，Zep 论文中的关系失效处理会比较新旧关系，并以摄入顺序处理更新。这适合某些个人记忆变化，却不能直接用于金融信息：一篇晚到的传闻不应废掉先前的官方事实。[Zep 论文](https://arxiv.org/html/2501.13956v1)

另外两项基础方法更贴合你们：

- **事件溯源**：把每次改变记下来，当前状态由这些记录形成，能够还原过去。[Event Sourcing](https://martinfowler.com/eaaDev/EventSourcing.html)
- **双时间**：分别记录事情何时成立，以及系统何时知道它，解决迟到和修订的问题。[Bitemporal History](https://martinfowler.com/articles/bitemporal-history.html)

**推荐保留三个不同的东西**

**一是原文证据。** 某个来源的某个版本，到底写了哪一句。

**二是关联记录。** 哪次处理决定把这条证据挂到哪个观点；后来有没有撤销或修正这条关联。

**三是判断记录。** 哪次调用看了哪些证据版本、哪些依赖版本，输出了什么状态和理由。

只保存第一项，仍然回答不了“当时为什么这么判”。

#### 时间至少要表达这些含义

| 含义 | 例子 |
|---|---|
| 事情发生／有效期间 | 许可从 10 月 1 日开始生效 |
| 来源公开日期 | 10 月 2 日发布公告 |
| 系统收到及处理的位置 | 10 月 3 日收到，分发序号 8127 |
| 修订被系统知道的位置 | 10 月 5 日收到修正版，序号 8360 |

“双时间”不意味着只能存两列日期。这里发生时间、公开日期和系统获知顺序都有用；未知的发生时间应保持未知。

实际处理顺序继续使用分发序号，不能用电脑时钟排序。

#### 晚到、修订和重跑应产生什么

以下是推荐的处理行为；未定的时间口径在最后单列。

| 事件 | 写什么 | 保留什么 |
|---|---|---|
| 新证据到达 | 证据、挂载决定、新判断 | 旧判断 |
| 同一输入重试 | 复用已提交结果，或继续未完成步骤 | 每次失败与拒绝原因 |
| 来源发修正版 | 新来源版本、修订关系、受影响的关联与判断 | 旧来源及其历史使用记录 |
| 第三方反驳旧说法 | 新证据及关联 | 原说法，不能假装它没出现过 |
| 模型／提示词改变 | 新配置版本；重跑产生新处理记录 | 原模型当时的输出 |
| 判断中途失败 | 保存尝试；不提交半份新状态 | 最后一次完整状态 |
| 依赖换格 | 通知记录、被通知者的新判断 | 精确的触发版本 |
| 到期且取得答案 | 答案和关闭记录 | 关闭前最后的预测 |
| 关闭后继续研究 | 新观点 ID、新梯子、新期限 | 原观点及原依赖历史 |

修订有两种不能混淆：

- “原文件把 55 写错了，修正为 45”：旧数字已被来源修正。
- “昨天要求许可，今天取消要求”：昨天的事实没有写错，是世界变了。

两者都会影响当前判断，但对历史的解释不同。

#### 一次重判，要保存完整的“输入清单”

至少包括：

- 观点及固定梯子的版本；
- 全部已挂载证据、证据版本及修订关系；
- 依赖观点的准确判断版本；
- 模型、提示词、输出结构、代码和配置版本；
- 实际请求、原始返回、引用检查结果；
- 最终状态、事实位置，以及各连线的方向说明。

这里应保存足以审计的输出和理由，不需要假定能够取得模型内部思考过程。

**历史回放有两种，必须分开：**

1. **还原当时**：读取原输入与原输出，恢复当时真正提交的状态。
2. **今天重算**：用某个明确配置再运行，得到一个新结果。

低 temperature 不能保证第二种逐字重现第一种。所以“能回放”应首先靠保存结果，而不是指望重调模型得到一样的答案。

#### “全部证据”不能变成搜索结果前十条

混合检索用于找证据应挂到哪些观点。一旦已经挂上，重判就应按记录取出该观点的全部证据及修订状态。

如果改成“每次只检索最相关的十条”，就是改变已定的判断方式。较早的反证可能没有被取到，状态会开始受查询措辞、索引版本和排名影响。

同样，被修正的证据应显示其修订关系，不能作为第二个独立有效数字继续计数，也不能从历史中抹掉。

#### 依赖血缘要区分“看过”与“换格”

A 的第 10、11 次判断可能同格。B 看过第 10 次，没有看第 11 次，不代表 B 应该重判。

因此应分别保留：

- 每次判断的版本：用于回答 B 当时究竟读了什么。
- 哪次判断发生换格：用于决定是否通知 B。

否则“版本落后就重判”会悄悄推翻已经定下的“只有换格才通知”。

此外，A 关闭后，新开的 A2 是新观点。不能悄悄把所有指向 A 的箭头改成 A2。B 原来依赖的 A 及其答案仍然存在；若要依赖 A2，应明确新增或更换依赖并留下记录。

#### 从观点查来源，与从来源查影响

推荐支持三种不同查询结果：

1. **挂载过**：来源里的哪些证据曾连到这个观点。
2. **实际读过／引用过**：哪些判断输入包含它，哪些输出明确引用它。
3. **沿依赖产生影响**：它触发了 A 换格，A 的某版又触发 B 重判。

第三种必须沿着真实的判断版本和通知记录追踪。不能沿当前依赖图走一遍，就宣称一条信息影响了所有下游观点。

W3C PROV 提供了适合借鉴的基本关系：数据实体、处理活动、生成、使用、派生、修订和引用。无需把整套标准实现一遍。[W3C PROV-DM](https://www.w3.org/TR/prov-dm/)

OpenLineage 则适合描述哪次任务读取、产生了哪些数据，但你们还需要细到“证据—观点—某次判断”的业务关系。只接入任务级血缘工具不够。[OpenLineage 数据模型](https://openlineage.io/docs/spec/object-model/)

#### 预测平台对“出答案”的启发

Metaculus 分开记录停止预测时间与预计判定时间；GJ Open 明确规定数据版本、迟发报告和政策宣布／生效的处理方式，其默认数据修订规则是按首次公布值判定，后续修订不改变原结果。[Metaculus FAQ](https://www.metaculus.com/faq/)、[GJ Open FAQ](https://www.gjopen.com/faq)

对你们的启发是：**固定的考题不仅要写看什么，还要写按什么来源、什么口径、哪种数据版本交卷。**

这属于问题和梯子本身的判定说明，不需要另恢复一套“证实／证伪条件”。

“现实正好属于五格之一”也不等于“系统已经拿到足够证据”。拿不到答案时不能填中性，更不能因为日历到期就假装已经判定。这里不建议恢复重建记录已经否决的“梯子不适用，自动关掉另开”机制。

## 2. 对 Alex 两个假设的结论，以及规模判断

| 假设 | 对在哪里 | 不够在哪里 | 什么时候需要 |
|---|---|---|---|
| 可能要用 embedding 匹配 | 能跨措辞、跨语言发现相关候选 | 相似不等于同一；也不能独自决定证据方向、来源独立性和日期口径 | 跨对象找关联、全库搜索、关键词召回出现明确遗漏时 |
| 像搜索引擎一样，拿候选观点直接搜索 | 适合生成需要比较的候选列表 | 不能搜到第一名就合并；挂证据还须用证据查询，不能只依赖候选观点的标题 | 候选范围较大、无法按对象直接取全时 |

**同对象去重的第一版不需要 embedding。跨对象证据检索可以采用混合检索，但应先证明它比对象、主题和别名查询多找回了什么。**

以下只是容量估算，不是实测：

- 假设 500 个研究对象、50 个主题，每个平均 2.5 条开放观点，共约 **1,375 条开放观点**。
- 假设每天 1,000 条信息，每条平均留下 5 条证据，一年约 **183 万条证据记录**。
- 开放观点很少，证据及判断历史持续增长；两者的存取策略不必相同。

在这个规模下，我的判断是：

| 技术 | 建议 |
|---|---|
| 关系数据库、来源版本、关联表、判断历史 | 从第一版就需要 |
| 按对象取全部开放观点 | 第一版主路径 |
| 全文检索 | 合理，亦便于查历史 |
| 对开放观点做向量搜索 | 可选；规模足够小，可先精确比较全部向量 |
| 独立向量数据库、近似最近邻集群 | 目前没有容量上的必要 |
| 图数据库 | 目前没有必要；依赖和血缘可以先用关系表、递归查询 |
| 独立重排服务、专门训练匹配模型 | 有实际质量或成本证据再加入 |
| 全套知识图谱自动抽取、社区摘要 | 超出当前问题需要 |

关系数据库可以表达图关系，PostgreSQL 也支持递归遍历；“有箭头”不意味着必须采用图数据库。[PostgreSQL 递归查询](https://www.postgresql.org/docs/current/queries-with.html)

**更需要预算的是重判成本。**

假设一条热点观点逐渐积累 1,000 条证据，每条占 50 个输入 token，每新增一条就全文重判：

- 最后一次约读 5 万 token；
- 整个累积过程约读 2,500 万 token，尚未计入其他提示内容。

这是算术示例，不是实际工作量预测，但说明了成本随累积证据数量近似平方增长。向量索引并不能解决这个问题。

第一版可以把**同一条信息同时提供给同一观点的多条证据一起提交、重判一次**。至于用摘要替代旧证据、只读部分证据，都属于对“全部证据重判”的实质修改，需要另行验证和决定。

未来验证时，至少分开看：

- 正确观点是否进入候选列表；
- 有正确候选时是否选对；
- 没有匹配时是否错误合并；
- 证据是否挂错／漏挂；
- 一条错误挂载通过依赖影响了多少观点。

不要只看一个综合准确率。H20／Blackwell 的错误合并，与一个无关小问题漏挂一次，投研后果不同。

## 3. 推荐的数据结构草图

下面是记录之间的关系，不是必须逐项建成独立服务或独立表。

```text
观点库
│
├─ 对象
│  ├─ 对象 ID、类型、名称
│  └─ 已知别名 → 同一个对象 ID
│
├─ 观点
│  ├─ 观点 ID、对象 ID
│  ├─ 看什么：数字／事件、范围、口径、事件阶段
│  ├─ 固定考题：问题、目标期间、到期日、五格、判定说明
│  ├─ 当前状态指针 → 最近一次已提交判断
│  ├─ 开放／关闭记录 → 关闭原因、答案记录
│  └─ 可选前后关系 → 接替哪条旧观点；不继承旧观点身份
│
├─ 来源版本
│  ├─ 上游 ID、上游版本、公开日期、收到时的分发序号
│  ├─ 原始内容快照或可验证的持久引用、内容校验值
│  ├─ 来源发行者；原始消息来自谁
│  └─ 修订／转载关系 → 另一个来源版本
│
├─ 证据
│  ├─ 证据 ID → 来源版本
│  ├─ 原文、段落／句子／表格位置
│  ├─ 事情发生或有效期间；数字所属期间
│  └─ 抽取解释版本 → 层、结构化数字、对象、修订关系
│
├─ 证据—观点关联
│  ├─ 证据 ID → 观点 ID
│  ├─ 哪次处理建立／撤销，关联理由
│  └─ 历次方向说明 → 由相应重判记录产生
│
├─ 观点依赖
│  ├─ B 观点 ID → A 观点 ID
│  ├─ 方向；建立／结束记录
│  └─ B 实际看过的 A 判断版本
│
├─ 处理与判断记录
│  ├─ 输入来源、候选列表、匹配／挂载决定
│  ├─ 全部证据版本、依赖判断版本、读取范围
│  ├─ 配置版本、实际请求、原始返回、检查结果
│  ├─ 输出：预测状态、事实位置、引用及连线方向
│  └─ 提交序号、前一判断、触发原因、换格通知
│
└─ 配置版本与检索索引
   ├─ 模型、提示词、输出结构、代码、匹配规则版本
   └─ 可重建索引：文本、向量、索引版本、收录到的序号
```

这里最重要的几个约束是：

- **证据正文不因观点不同而复制**，多条关联引用同一证据。
- **方向不是关联的一次性属性**，它属于某次判断对这条关联的解释。
- **原文与模型解释分开**，重新抽取不应抹掉先前的层分类和结构化结果。
- **索引不是主存**，重建索引不能改变来源、观点身份或历史判断。
- **同一判断的状态、连线解释和待通知记录一起提交**，避免状态已改变、通知却丢失。
- 保留每个对象的单写入者；跨对象写入仍走带分发序号的消息。两个候选同时认为“没有旧观点”时，第二个提交前必须重新核对，不能各自建一条。
- 新模型的候选结果可以留作比较；只有明确提交后才成为当前状态。配置改变不能隐含地重写历史。

## 4. 我最不确定的三点

**第一，“同一件东西”的边界能否在真实输入中稳定辨认。**

H20 和 Blackwell 很容易说明；“中国数据中心收入”“中国 AI 芯片收入”“中国客户贡献的收入”就未必。对象别名通常不难，业务口径才是主要风险。

我会先用真实候选整理“应合并、应分开、信息不足”的成对案例，尤其加入中英文、宽窄范围和明确不匹配的情况。这里没有现成论文能替你们决定正确边界。

**第二，晚到信息到底读哪个时点，以及修订后按哪个答案评价。**

[D31](/Users/lchingen/hivemind/docs/DECISIONS.md:602) 写的是：晚到信息读取其公开日期的历史版本；重建记录的新表述则是：从全部证据和依赖现状重判。两者需要明确“现状”所指的时点。

我的倾向是分别提供：

- 当时实际知道什么、实际怎么判；
- 后来收到的信息如何改变今天的判断；
- 今天如何修正对过去事实的认识。

数据结构应能表达三者，但不能让实现自行选择。已经关闭的观点若遇到来源修订，是否改变原评分，同样需要事先约定；GJ Open 的首次公布值规则只是一个可参考选择。

**第三，热点观点的全部证据会增长到什么程度。**

数据库规模大体可控，长期重判的上下文长度、成本和遗漏反证的风险更难估计。需要真实观察美联储、出口管制这类热点观点：

- 半年究竟积累多少独立来源；
- 转载和修订占多少；
- 模型读完整证据时能否稳定引用关键反证；
- 若未来采用压缩，是否保持与全文判断一致。

在这些数据出来之前，我不建议为节省 token，直接把“全部证据”换成摘要或 Top-K 检索。
