## Verified path and one case

`clean-arch/e2e-2026-11-09/adapter.py` is an experimental seeded diagnostic, not clean production integration. For a Step 2 revision, it writes the relation and inherits old evidence's question links to the new evidence. The existing frozen judge can then receive this new evidence and an explicitly qualified, unverified matcher relation (`src/hivemind/views/judging.py`). The store returns only the last-written revision relationship for each evidence item (`src/hivemind/views/store.py`); therefore the displayed relation and the relation responsible for inheriting a question can differ.

For the completed D392 d1 saved run, record `70:e4` directly names only v18, the Kyber NVL144 shipping question. Its later statement is an NVIDIA spokesperson's response to a Kyber-delay report. The adapter writes it as `e185`. A source-reader-supported wrong relation from `69:e5`/`e181`, which describes a plan to sell more Oberon-rubin racks, makes `e185` inherit v20, the FY2027 Blackwell/Rubin revenue question. Checking all five recorded old evidence items shows only e181 has v20. The same new item also inherits v7 from `e143`, whose source-level relation is uncertain.

The actual saved judging archive contains `e185` together with a later-version marker naming `e131` in 23 historical request objects (v18 5, v7 9, v20 9; per-evidence block checked). The ledger's v20 and v7 judgements each cite e185 eight times. These counts repeat the same item across dates/requests and may include repeated calls; they are not independent errors. They establish an exposure path, not that the wrong e181 relation changed a judgement, that the e131 display was valid, or that e185 is necessarily irrelevant to v20. Its relevance to a revenue question must be judged separately. The historical writer keeps both evidence items in force and labels the matcher relation as opinion, not verified fact.

## One bounded next test

Use a scratch copy of the real Step 2 library and the existing D392 adapter. First run an untouched offline control that reconstructs historical judge requests and business state from the saved responses. Then change only the `69:e5 → 70:e4` relation in a separately labelled scratch copy; keep evidence, all other relations, record order and dates. Replay and stop at the first batch in which an original judge request changes, disappears or a new one would be needed. Record the actual changed links, triggered views, evidence selection and current state. Independently check whether the source of `70:e4` would be useful to v20 on its own; deletion of an unsupported relation must not be treated as proof that removing the evidence is desirable. If the reconstruction fails, stop and report the failure; do not present a handcrafted one-request edit as an end-to-end replay. A different hypothetical path that omits e185 could itself lose relevant evidence.

The untouched offline control is not implemented or verified yet. `adapter.replay` creates an empty output archive; a transport that simply refuses everything fails on its first original call. A practical existing starting point is `clean-arch/e2e-2026-11-09/control_v108.py`'s read-only reference transport: only exact canonical request matches may receive the corresponding stored full response; unknown requests must stop without network. The completed historical d1 judging archive contains 229 normal and 10 refused rows; all 239 stored responses were read-only checked as parseable and matching stored answers, but this does not establish that complete replay will match. The offline control must respect historical rejection/retry, request ordering, dispatch concurrency and exact input trace/library identities. The archive stores sorted canonical request JSON; that alone does not prove the historical outbound HTTP byte order. Compare normalized business state and requests without discarding factual dates or call ordering, and disclose what can actually be checked. Current judge stages can fan out, so a mismatch may be a first divergence **batch** rather than a unique first call.

If the corrected edge changes the authentic input, a separately scoped same-day original-versus-counterfactual judge probe could assess the effect on that single judgement's result, reasons and citations relative to control variability. This is not run or priced in this council. A deterministic replay can show input divergence, not the answer to a changed model request; responses after divergence cannot be reused as if the question had not changed. If no change is observed, it is a negative result only for this edge, view and path; if a result does change, that is evidence of sensitivity, not proof the removal is more accurate or broadly important. A finding that motivates a change to what the system stores or inherits is a product decision under the existing rules.

Claude also initially proposed a transport that refuses every request; on challenge it retracted this because the replay creates an empty archive. The attempted correction is a design, not a claim that the offline replay currently works.
