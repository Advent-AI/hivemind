## 一句话

抽取只做一件事：每条信息整份交给模型，用资深对冲基金分析师的视角、按这一类的提示词，读出观点（thesis）和证据，每条带出处，交给观点库。

## 为什么这样设计

- 系统做的事是建立、更新和关掉观点库里的观点（D26），抽取就是把每条信息读成观点和证据。怎么和已有观点对上、写进库，是观点库的事，不在这里。
- 推进来的每条信息都整份交给模型读：文件连同里面的表格一起读，表格数据一次发布整批读，不按文字、表格分开处理。
- 不同类别该读的东西不同：新闻读发生了什么、消息从哪来；研报读作者的看法和评级；政府决定读决定本身和生效时间。所以每个类别一份提示词，都用同一个提示词模板拼出来。
- 观点是模型（分析师）的判断；谁在哪条信息里说了什么，是客观的证据。
- 每条观点和证据都带出处，以后能快速回到原文去查、去推理。

## 一条信息，一步一步

模型只做第 2 步，其余是代码。

<!-- generated: steps -->
```
一条信息进来（带类别和顺序号）
  ↓ 1 拼提示词（代码）：按这条信息的类别，用同一个提示词模板拼出这一类的提示词
  ↓ 2 读（模型）：整份读完，写出候选观点（主张、主题层还是对象层、讲的是谁、驱动、方向、期限档、利好还是利空、理由、前提、检验条件）和证据（原文、谁说的、原始来源、哪一层），每条带出处
  ↓ 3 核对出处（代码）：原文那一句在不在这条信息里、数字在不在那一句或那一格里；对不上的不要，记下原因
  ↓ 4 交给观点库（代码）：带着顺序号，交给观点库去对上、写进去
```
<!-- /generated: steps -->

## 提示词模板

所有类别用同一个提示词模板，由这五块拼成这一类的提示词；这一类的读法取自分类规则，不另写。

<!-- generated: template -->
| 部分 | 写什么 | 从哪来 |
|---|---|---|
| 角色 | 你是一位资深对冲基金分析师。读这条信息，是为了形成和检验对公司、资产和主题的观点：写出你的观点，以及支持或削弱它的证据。 | 所有类别一样 |
| 这一类是什么、怎么读 | 这一类的定义和读法，比如“看法和估计算作者说的，不当成已经发生的事”。 | 取自分类规则，这里不另写 |
| 讲的是谁 | 这条信息的相关对象。 | 这条信息的标签 |
| 这一类要读出什么 | 见下面的表，每类一行。 | 抽取模块 |
| 这些对象已有的驱动 | 只给驱动的名字，不给观点的方向和证据：让模型知道该注意什么，又不被已有的观点带着走。 | 观点库 |

## 每一类有自己的提示词

下面是拼好的一份，以 T7 新闻为例。

<!-- generated: prompt -->
```
T7 新闻的提示词（同一个提示词模板，第 2、4 块换成新闻这一类的）
├─ 1 角色 → 资深对冲基金分析师（读这条信息，是为了形成和检验观点：写出你的观点，以及支持或削弱它的证据）
├─ 2 这一类怎么读 → 媒体的报道（取自分类规则：媒体发的内容，除了评论和分析（那归 T8）；媒体登记过的发布系列按系列归类）
├─ 3 讲的是谁 → 这篇报道的相关对象（由代码填，比如 NVDA、AMD）
├─ 4 要读出什么 → 发生了什么事、什么时候、涉及谁；消息从哪来，原始来源是谁（官方确认的算发生的事；“知情人士称”算传闻）
└─ 5 已有的驱动 → 这些对象已有驱动的名字（由代码填，比如“美国对华 AI 芯片出口管制”）
```

- 每一类都有自己的提示词：同一个提示词模板，第 2 块（这一类怎么读）和第 4 块（要读出什么）换成这一类的；第 1 块所有类别一样；第 3、5 块由代码按这条信息填进去。
- 研究对象会看的 15 类（T1–T15）各一份；T16 研究对象默认不看，用到时再写。
- 输出的格式（候选观点、证据、出处各有哪些格子）由代码规定和检查，不写进提示词。
- 每一类提示词的具体写法，建的时候在存下的信息上试过再定；每一版记在 Config 里，改一次就是一个新版本。

## 16 个类别：每一类读出什么（提示词第 4 块）

<!-- generated: categories -->
| 类别 | 这一类要读出什么 | 证据一般在哪一层 |
|---|---|---|
| T1 业绩发布 | 实际数、指引、管理层的解释；检验条件要用的数 | 实际数是发生的事；指引和解释是当事人说的 |
| T2 定期报告 | 实际数、分部数；风险因素和业务描述里讲到的风险和变化 | 数是发生的事；风险和变化是当事人说的 |
| T3 法律与资本市场文件 | 交易条款（价格、对价、交割条件、时间表）；各方的说法和诉求 | 条款是发生的事；说法是当事人说的 |
| T4 电话会文字稿 | 管理层对关键问题的回答、口径的变化；分析师追问的焦点 | 回答是当事人说的；追问是第三方看法 |
| T5 演示材料 | 管理层给的中长期目标、资本配置的框架、新业务的规模 | 当事人说的 |
| T6 公司其他发布 | 发生了什么事（高管变动、并购、新产品、回购）；公布的经营数字（比如交付量） | 发生的事 |
| T7 新闻 | 发生了什么事、什么时候、涉及谁；消息从哪来，原始来源是谁 | 官方确认的算发生的事；“知情人士称”算传闻 |
| T8 观点与分析 | 作者的看法、论据、预测、评级和目标价，以及它们的变化（用来算共识） | 第三方看法 |
| T9 访谈记录 | 说话人讲的经营情况（订单、价格、份额、库存）；他凭什么知道 | 第三方看法 |
| T10 官方行动与记录 | 决定或行动本身、什么时候生效、影响谁；后面的程序（上诉、截止日），适合写成检验条件 | 发生的事 |
| T11 宏观政策与统计 | 公布的数字和政策决定，和上一次比差多少；官方措辞的变化 | 数和决定是发生的事；措辞是当事人说的 |
| T12 市场价格与成交 | 价格和成交的变化，对着检验条件看 | 发生的事 |
| T13 持仓与资金流 | 谁在买、谁在卖、规模多大 | 发生的事 |
| T14 日历 | 排定的日期，用作检验条件的期限或催化剂 | 发生的事 |
| T15 第三方测量 | 测到的经营数据，作为量化证据 | 发生的事（注明是第三方测的） |
| T16 参照数据 | 研究对象默认不看 | — |

每份文件都整份交给模型，里面的表格一起读；表格数据一次发布算一条，也整批交给模型。申报里的 XBRL 数字不另外推，文件本身已经有这些数；检验条件要准确的数时，由 Pull 模式去查。

## 例子：NVDA 的 8-K 读出什么

<!-- generated: example -->
```
NVDA 的 8-K · 2025-04-15｜读出两条候选观点（T6 公司其他发布：H20 出口中国要许可证，预计计提约 55 亿美元）
├─ 主题层 → 未来一年美国对华 AI 芯片出口管制会收紧（证据：“H20 出口中国要许可证”（发生的事，NVDA 披露）；证伪条件：美国批准 H20 对华出口）
└─ 对象层（NVDA） → 一年内中国数据中心收入基本归零（利空）（前提：上一条；证据：“预计计提约 55 亿美元”（当事人说的，公司自己的预计）；检验条件：中国区收入同比降 50% 以上（NVDA 只公布中国区总收入，用它来量））
```

出处：两条证据都记 8-K 的上游编号和版本、所在段落和原文那一句；代码核对“55 亿美元”确实在那一句里。读完就交给观点库，怎么对上、写进去，见观点库。例子用 NVDA，美股、期货、加密货币都走同一套。

## 出处记什么

<!-- generated: sources -->
```
一条出处
├─ 哪条信息 → 上游编号和版本（凭它去团队的库里取原文）
├─ 哪一类、哪天 → 类别、发布日
├─ 哪一处 → 第几节第几段、表里哪一格（表格数据写数据集和记录编号）
└─ 哪一句 → 原文那一句（代码核对它真的在这条信息里，数字真的印在那一句或那一格里）
```

- 每条观点、每条证据、每一次变化都带出处；观点的主张和理由写明依据哪几条证据。
- 抽取核对：原文那一句不在这条信息里、数字不在那一句或那一格里的，不交出去；观点库核对：出处在处理记录里查不到的，不写进库。都记下原因。
- 两头都能查：从一条观点查到它的全部来源信息，从一条信息查到它产生和改动过的全部观点和证据。
- 原文不存，凭上游编号去团队的库里取。
<!-- /generated: sources -->

## 验收标准

- 每条交进来的信息都整份交给模型，用这一类的提示词；用的是哪版设置，记在处理记录里。
- 每条观点和证据都有出处。原文那一句不在这条信息里、数字不在那一句或那一格里的，不交给观点库，记下原因。
- 抽取不改观点库：它只交出候选观点和证据。
- 失败从失败的那一步重试；重试只替换自己上次的结果。

- D26：观点库是系统的核心；每条都带出处。
