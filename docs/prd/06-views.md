# 观点库（thesis · ladder · evidence）

> 状态：设计中 · 更新：2026-10-18 · 依据：docs/DECISIONS.md D7、D11、D12、D16、D26、D27、D29–D31、D33
> 设计页：docs/system-design.html › New › 观点库 › 展开。本文和 DECISIONS 不一致时，以 DECISIONS 为准，并改本文。

## 一句话

系统的核心。系统做的事，就是建立、更新和关掉这里的观点：抽取交来的观点和证据在这里去重、对上已有的驱动、写进库；对象下面挂驱动，驱动下面挂观点，观点下面挂证据、检验条件（ladder）和前提。

## 为什么这样设计

- Alex：“整个 system 做的事情就是建构，更新，删除这个 data structure。”观点库就是原来设计页上的 thesis · ladder · evidence；原来的研究库并进来，不再单独存一大堆事实。
- 观点是模型（分析师）的判断；谁在哪份文件里说了什么，是客观的证据。一条观点像一个因子：由一串量化和非量化的证据支撑。
- 宏观类的观点在公司层次之外，所以分两层：主题层讲世界上会发生什么，对象层讲某个对象会怎样，用“前提”连起来。两层的对错各算各的，证据来源也不一样。
- 证伪或过期的观点关掉，但留在库里供查历史。
- 新观点和已有观点比，身份放在“驱动”上，embedding 只用来找候选。研究显示 embedding 分不清方向、数字和时期（“收紧”和“放松”在它看来很像），而成熟的系统都是先定一个固定的键，再在键里面比（见 `reports/观点库 向量检索 去重匹配.md` 和 `reports/观点库匹配 业界做法对比.md`）。
- 旧系统的教训决定了几条规则：观点越长越多（有一轮 META 长出 27 条，其中约 10 条分析师看只该算 2 条）→ 身份放在驱动上，同一驱动同一期限档只有一条有效观点；合并合错了改不回来 → 合并只是改指向，可以撤回；观点从来不退出（一轮 143 次维护里退休 0 次）→ 每条观点都有期限，到期由 Pull 模式送最终判定；改写后分不清还是不是同一条（81% 的情景描述每次改写都换了措辞）→ 主张写下不改，要改就新建一条接替旧的。

## 抽取交来的观点和证据，怎么写进库

模型只做第 3 步，其余是代码。

<!-- generated: write -->
```
抽取交来的候选观点和证据
  ↓ 1 证据去重（代码）：原始来源、讲的事或指标、日期或财期都一样：只多记一个出处
  ↓ 2 找候选驱动（代码）：这份文件相关对象的全部驱动，加上从全部主题驱动里用关键词和 embedding 搜到的几条
  ↓ 3 对上（模型）：短调用，不带全文：属于哪个驱动、新驱动还是拿不准；前提是哪条；有没有重复的证据
  ↓ 4 定（代码）：按下面的判断树：加证据、新建观点或新建驱动
  ↓ 5 查要不要判（代码）：符合触发条件的观点，交给最终判定
```
<!-- /generated: write -->

## 第 4 步：代码怎么定

<!-- generated: decide -->
```
一条候选观点｜模型说它属于哪个驱动？（驱动和观点的编号只能是候选里的，越界由代码拒绝）
├─ 已有的驱动 → 找同一期限档的有效观点｜有吗？（同一个驱动、同一个期限档只有一条有效观点）
│   ├─ 有 → 比方向｜方向一样吗？
│   │   ├─ 一样 → 挂成支持证据
│   │   └─ 相反 → 挂成削弱证据（不另建一条反方向的观点）
│   └─ 没有 → 在这个驱动下新建观点
├─ 新驱动 → 新建驱动和观点（Pull 模式定期合并驱动时会再看到它）
├─ 拿不准 → 照样新建，标“待复核”（同时放进人工复核池）
└─ 名单外的对象 → 放进人工复核池（观点和证据先挂“未知对象”）
```

- 同一份文件，先写主题层，再写对象层，对象层看到的是刚更新过的前提。
- 数字类的检验条件用固定格式写：指标、哪段时间、怎么算、怎么比、门槛多少，全系统一段代码来判；需要新的写法，就加一种格式。
<!-- /generated: decide -->

```
    └─ 定 → 新建 NVDA 观点（前提指向左边的主题观点，记“看过第 1 版”）
```

## 结构：对象 → 驱动 → 观点

<!-- generated: structure -->
```
观点库
├─ 对象 → 公司、加密货币、商品、主题（都来自研究对象名单）
│   └─ 驱动 → 写得具体：谁、做什么、对哪儿（例：美国对华 AI 芯片出口管制。定义写下不改，要改就新建，旧的指过去）
│       └─ 观点 → 一句主张，加方向和期限（主张写下不改；要改就新建一条，接替旧的）
│           ├─ 挂着 → 证据（原文、出处、谁说的、原始来源、哪一层、支持还是削弱）
│           ├─ 挂着 → 检验条件（ladder）（证实和证伪，各带期限；只能加，不能删也不能放宽）
│           └─ 可以有 → 前提（指向另一条观点，记着上次看过它第几版）
└─ 另记 → 处理记录（每份文件处理到哪一步；分发靠它判断以前处理过没有）
```
<!-- /generated: structure -->

驱动的定义写下不改；要改就新建一个驱动，旧的指过去。

## 两层：主题观点在上，对象观点以它为前提

<!-- generated: levels -->
```
主题“芯片出口管制”
└─ 驱动 → 美国对华 AI 芯片出口管制
    └─ 主题观点 → 未来一年管制会收紧（证据：商务部规定、官方表态、关于这件事的新闻）
        ├─ 以它为前提 → NVDA：一年内中国数据中心收入基本归零（利空 · 证据：NVDA 自己的 8-K、业绩稿）
        ├─ 以它为前提 → AMD：MI308 对华收入受损（利空 · 证据：AMD 自己的 8-K）
        └─ 以它为前提 → TSM：来自中国客户的收入下降（利空 · 证据：管理层说“如果……会……”）
```

- 驱动是世界上的事（政府政策、宏观数据、整个行业的供需），而且名单里有对应的主题：观点挂在主题层。
- 驱动是这个对象自己的事：观点挂在对象层。
- 是世界上的事，但名单里还没有这个主题：先挂在对象层，同时放进人工复核池，建议新增主题。主题只能来自名单，系统不自己造主题。
- 世界上发生了什么，证据挂在主题观点上；公司自己的数字和说法（包括“如果……我们会……”）挂在对象观点上；一份文件可以两层都挂。
- 一条主题观点影响哪些对象，不另存名单，查“哪些观点以它为前提”就有。一只股票的全貌，就是它自己的观点加上这些观点的前提，同一个宏观因素只算一次。
- 前提也可以指向别家公司的观点（比如供应链）；代码检查不能绕成环。
<!-- /generated: levels -->

## 前提变了，靠它的观点怎么办

前提像一个软链接：指向另一条观点的编号，跟着它走（它被合并时自动改指向），同时记着上次看过它的第几版。

<!-- generated: propagation -->
```
前提观点变了｜变的是什么？（前提记着上次看过第几版；新版本出来，就是落后了）
├─ 状态变了 → 马上送最终判定（证伪、过期、证实、被接替、不再跟踪：“前提变了，这条还成立吗？”）
├─ 被合并 → 代码改指向（标“前提有更新”）
├─ 被削弱 → 送最终判定（这个对象下一份文件进来时；最迟 7 天，由 Pull 模式兜底）
└─ 被支持 → 不处理（只多一个版本号）
```
<!-- /generated: propagation -->

## 证据分四层，上层说了算

<!-- generated: tiers -->
| 哪一层 | 例子 | 能做什么 |
|---|---|---|
| 发生的事 | 官方动作、公布的数字、已经发生的交易 | 能满足检验条件 |
| 当事人说的 | 公司指引、管理层表态、官员讲话 | 只能让观点变强或变弱 |
| 第三方看法 | 卖方、媒体分析、专家、经济学家的预测 | 只能让观点变强或变弱；用来算共识 |
| 传闻 | “知情人士称”、没有出处的消息 | 只能让观点变强或变弱 |
<!-- /generated: tiers -->

## 说法互相矛盾时

同一个观点被不同来源、在不同时间说成相反的样子，是常态，验证本来就是这样发生的。处理办法照分析师的做法：不投票，先分层，数独立来源，找出能一锤定音的事实。

<!-- generated: conflicts -->
- 不投票：上层说了算。只凭第三方看法和传闻，不能把观点关掉。
- 数独立来源，不数条数：按原始来源数，20 家媒体转述同一条独家算 1 家。
- 出现分歧（同一层里，独立来源有的支持、有的削弱）：送最终判定，把能一锤定音的事实写成新的检验条件：什么事实，什么时候能知道。
- 检验条件只能加，不能删，也不能放宽，防止事后挪球门。
- 关键问题被事实回答以后，代码把早先对着它的说法标成“后来被证实”或“后来被否认”。每个来源说得准不准，就攒成了记录；这份记录先只展示，不用来给证据加权。
- 共识由代码算：对每条观点，每个独立的第三方来源只取它最新的立场，汇总成分布，就是“市场怎么看”。我们读到的来源只是市场的一部分。
<!-- /generated: conflicts -->

## 例子：主题观点“未来一年美国对华 AI 芯片出口管制会收紧”

| 时间 | 谁说的 | 哪一层 | 说了什么 | 对这条观点 |
|---|---|---|---|---|
| 2025-04-15 | NVDA 8-K | 发生的事 | H20 出口要许可证 | 支持 |
| 2025-04-16 | AMD 8-K | 发生的事 | MI308 也要许可证 | 支持 |
| 2025-04 | 20 家媒体 | 发生的事 | 同上（转述，原始来源都是 NVDA 的 8-K） | 不另算 |
| 2025-07 中 | NVDA 声明 | 当事人说的 | 美国政府保证会批准 H20 许可证 | 削弱 |
| 2025-07（示意） | 卖方 A | 第三方看法 | 许可只是谈判筹码，管制的大方向不变 | 支持 |
| 2025-08（据报道） | 报道官方动作 | 发生的事 | 商务部开始发 H20 许可证，条件是上缴 15% 的中国收入 | 削弱，满足证伪条件 |

到 7 月证据两边都有：NVDA 的声明（当事人说的）削弱，卖方 A（第三方看法）支持。两条不在同一层，也没有“发生的事”来削弱，不触发最终判定；观点留着，两边的证据都展示出来。能一锤定音的，就是证伪条件里写的那件事：美国会不会真的批准 H20 对华出口。8 月据报道商务部开始发许可证，证伪条件满足，送最终判定，这条主题观点判为已证伪。以它为前提的 NVDA 观点“一年内中国数据中心收入基本归零”再判一次：据报道中国要求企业不要采购 H20，中国收入仍没回来，所以留下，前提换成一条新的主题观点。

## 一条观点有哪些部分

<!-- generated: fields -->
| 部分 | 写什么 | 例子 |
|---|---|---|
| 层 | 主题层讲世界上会发生什么；对象层讲这个对象（公司、加密货币、商品）会怎样 | 主题层 |
| 主张 | 一句话，写下不改 | 未来一年美国对华 AI 芯片出口管制会收紧 |
| 方向和期限 | 上升或下降；期限档（短期或长期），加到期日。同一个驱动下，同一个期限档只有一条有效观点 | 上升；短期，到 2026-04-15 |
| 利好还是利空 | 只有对象层有：这个驱动对这个对象的影响方向，不是买卖立场 | NVDA 那条：利空 |
| 理由 | 为什么这么看，写明依据哪几条证据 | H20 出口要许可证，公司预计计提约 55 亿美元 |
| 前提 | 指向另一条观点（通常是主题观点），同时记着上次看过它第几版 | NVDA 那条：以管制会收紧为前提，看过第 1 版 |
| 检验条件（ladder） | 证实条件和证伪条件，各带期限；数字的由代码判，事件的由模型判；只能加，不能删也不能放宽 | 主题观点的证伪条件：美国批准 H20 对华出口 |
| 我们和共识哪里不同 | 可以空着；共识由代码算 | — |
| 状态 | 有效、已证实、已证伪、已过期、已并入、被接替、不再跟踪 | 有效 |
| 历史 | 每变一次多一版，记下哪天、因为哪份文件；旧版都留着 | 2025-04-15 新建 |

## 一条证据记什么

<!-- generated: evidence -->
| 部分 | 写什么 |
|---|---|
| 原文 | 文件里的那一句，或表里的那一格 |
| 出处 | 上游编号和版本、类别、发布日、在文件里的位置 |
| 谁说的 | 说这句话的人或机构 |
| 原始来源 | 转述的，指向最初说这句话的人；按它数独立来源 |
| 哪一层 | 发生的事、当事人说的、第三方看法、传闻 |
| 支持还是削弱 | 对这条观点 |
| 对着哪条检验条件 | 在回答哪个关键问题；没有就不填 |
| 后来的结果 | 关键问题被事实回答以后，代码标上“后来被证实”或“后来被否认” |
<!-- /generated: evidence -->

## 先后和同步

<!-- generated: order -->
- 只有文件能产生证据；观点之间只传通知，不传证据，所以观点不会自己证明自己。
- 每条观点只有一个写入者：主题观点由主题的队列写，对象观点由对象的队列写。别的文件给它的证据，带着那份文件的顺序号，作为一条消息交给它的队列。
- 一份文件只读顺序号比它小、而且发布日不晚于它的文件留下的状态，加上它自己已经写下的；同一天的文件按顺序号排，不看几点几分。结果必须和一份一份按顺序处理完全一样，并行只是为了快；并行时读到的观点在提交前变了，就重新判断一次。
- 晚到的文件（发布日比已经处理过的还早）：读它发布那天的版本，不偷看以后；写的时候排在最后，证据上记它真实的发布日。
- 同一份文件的修正版：新版的证据替换旧版的，旧版留在历史里；修正后某条观点没了依据，送最终判定。
- 失败：每份文件记下做到了哪一步；从失败的那一步重试，重试只替换自己上次的结果；多次失败的放进人工复核池。
- 对象被移出名单：它的观点保留，标“不再跟踪”，到期不判。
<!-- /generated: order -->

## 处理记录

每份处理过的文件一行：上游的编号和版本、顺序号、去处、做到了哪一步、结果，以及当时用的 Config 版本。分发靠它判断“以前处理过没有”；从一份文件查它改过哪些观点，也靠它。

## 验收标准

- 模型给的驱动和观点编号不在候选里，一律拒绝。
- 方向相反的说法挂成削弱证据，不会另建一条反方向的观点。
- 同一件事被多家转述，只算一条证据，其余记成出处。
- 同一份文件先写主题层，再写对象层。
- 每条观点、证据和每一次变化都有出处，从观点能查到全部来源文件，从一份文件能查到它改过的全部观点和证据。
- 观点和驱动的主张、定义不会被改写；改动只会生成新版本或新条目，旧的都留着。
- 同一个驱动下，同一个期限档只有一条有效观点。
- 只有文件能产生证据；观点之间不互相写证据。
- 检验条件只会增加，不会被删除或放宽。
- 只凭第三方看法和传闻，观点不会被判成已证实或已证伪。
- 前提不会绕成环；前提的状态变了，以它为前提的观点都会被送到最终判定。
- 一份文件读到的状态，只来自顺序号比它小、发布日不晚于它的文件；并行处理的结果和一份一份按顺序处理完全一样。

## 还没定的

- 驱动目录怎样维护：Pull 模式定期合并和拆分的具体做法；新驱动由一处写入，避免两个对象的队列同时建出同一个驱动。
- 名单加了新对象、上游补推它的历史时，补推的旧文件可能另建出重复的观点，靠定期合并收拾。
- 存在哪里、用什么数据库，和建的时候一起定。
- 真建之前要在存下的数据上量：每个对象挂多少驱动和观点；两次独立标注“是不是同一个驱动”的一致度；判“新驱动”准不准；候选清单换个顺序，答案会不会变。
