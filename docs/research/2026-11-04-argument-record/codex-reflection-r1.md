**1. Root cause—and corrections to the diagnosis**

The implementation joins three decisions that need different treatment:

- **What the sources say.** The card’s sentence can mix reported facts, the model’s calculation and its interpretation. There is no separate place identifying each.
- **What survives into the next judgement.** Only sources cited by the latest card survive beyond the three-judgement arrival window.
- **What counts as support.** The same sentence carries evidence references and an “independent sources” count, even when its decisive number is the model’s extrapolation.

The code checks reference membership, lengths, retained identifiers and other structural rules. It cannot establish that the cited sources support the sentence or that its independence count is right. Moreover, the judgement’s citations are themselves derived from the card, so they provide no separate record of material the judgement used but the card omitted. ([Schema](/Users/lchingen/hivemind/src/hivemind/views/judging.py:343), [selection](/Users/lchingen/hivemind/src/hivemind/views/judging.py:379), [checks](/Users/lchingen/hivemind/src/hivemind/views/judging.py:466), [writing](/Users/lchingen/hivemind/src/hivemind/views/judging.py:541))

That produces a reinforcing sequence:

**Choose an explanation → retain sources that fit its short account → present that explanation as the standing case → reconsider from that narrowed material.**

D201 requires a versioned argument and its sources. It does **not** require the latest short argument to determine which older sources remain readable. That additional choice comes from draft 8, §3. ([D201](/Users/lchingen/hivemind/docs/DECISIONS.md:2584), [design §3](/Users/lchingen/hivemind/docs/research/2026-11-04-argument-record/design.md))

**2. Structural options**

These are proposals, not demonstrated solutions. None can honestly promise loss-free judgement from the existing evidence.

| Option | Structural rule | What it solves—and loses |
|---|---|---|
| **A. Keep v7’s window; add the card only as a record. Do not read it back.** | Write the argument after the unchanged judgement, in a separate operation that cannot change its input, citations or dependencies. | Removes card feedback and gives people a versioned explanation. **Does not solve D358’s growing requests or fully satisfy D201’s requirement that judgement read the argument.** It is a recovery baseline, not the final design. |
| **B. Do not read the card back; read original sources through bounded pages.** | The judge reads source material in manageable batches and can reopen any source. The argument is an output for people, not an input to future judgement. | Removes recursive argument rewriting and can bound individual requests. Total reading can still grow. It also requires an explicit revision to D201’s argument-reading requirement. |
| **C. Read the argument as a revisable explanation; keep source access independent of it.** | Separate reported statements, our calculations, assumptions and dependency conclusions. Keep the argument’s history, but never make its latest citations the only route to older evidence. The model can search and reopen the complete, historically correct source collection. | Best fit to D201 and a route toward smaller requests. E106 remains recoverable after disappearing from the summary. Retrieval can still miss important material; merely adding labels to the current card would not suffice. |
| **D. Rebuild the argument from a complete source review when a judgement event occurs.** | A reader examines all in-force sources in bounded batches, writes a fresh argument with exact supporting passages, and the judge reads that argument and its sources. Earlier arguments remain available for comparison, not as substitutes for the review. | Gives every older source another reading opportunity and satisfies D201. Bounds each request, but adds calls, latency and growing total work. The reader can still omit or misinterpret something when composing the argument. |

A is grounded in the existing v7 path; B–D separate source reading from the card-controlled selection introduced in draft 8. D358 demands attention to both large requests **and** the burden of writing many evidence identifiers; changing input access alone does not address both. ([v7 path](/Users/lchingen/hivemind/src/hivemind/views/judging.py:192), [draft 8 §§3–4](/Users/lchingen/hivemind/docs/research/2026-11-04-argument-record/design.md), [D358](/Users/lchingen/hivemind/docs/DECISIONS.md:3782))

For B–D, code would own identifiers, source versions, exact passage retrieval and batch sizes. The model would still decide relevance, source independence and forecast weight. No code rule would prescribe year-over-year growth, a particular financing discount or industry-specific factors. All work would run only within the existing judgement event; any changed judging contract would receive a new version. These boundaries follow your supplied AGENTS §§2 and 6 and the existing separation of external evidence from our conclusions. ([PRD](/Users/lchingen/hivemind/docs/prd/06-views.md:127))

**4. My lean**

I would pursue **C**, using **A as the recovery baseline**: keep a versioned research argument, but take away its power to make older sources disappear from the judge’s reach. Separate what was reported from what we calculated, preserve the exact dependency versions, and let the judge reopen sources independently of yesterday’s explanation.
