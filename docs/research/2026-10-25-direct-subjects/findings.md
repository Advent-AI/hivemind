# 入库时自动归组：核心路径已经跑通

在本次 NVIDIA 的四篇原文、三个样本流上，三个都跑通了：两个不同里程碑归入同一 Rubin 组，后来风险沿原观点进入这个组，新增的卫星应用也复用这个组。这个结果证明了核心路径可行，不代表全公司、全行业或大规模效果已经验证。

## 实际得到什么

三个样本中的 Rubin 组都有这三条独立观点：

```
Vera Rubin 推出与采用
├─ 2026 年下半年能否开始量产出货
├─ SK 的第一座 Rubin AI 工厂能否在 2027 年上线
└─ SpaceX 的 Rubin 卫星能否在 2027 年开始发射
```

供应延迟的报道仍连在“出货”观点上，组从这条真实证据连线读到风险。没有把三条观点合成一个问题，也没有给组虚构一个总分。以上是实验原文中的计划和问题，不是确认这些未来事件已经发生。

## 真正挡住流程的三件事

**第一，问错了问题，也重复做了决定。** 旧匹配问“SK 工厂计划和 Rubin 推出是否同一件事”。当然不是，但 SK 的部署观点属于 Rubin 采用过程。两份真实失败答复都已经看到旧 Rubin 组，仍因为“不同部署计划”另建组；搜索和写入没有丢失它。

现在只在读全文时决定归属：每个候选观点必填所属组，直接引用展示的旧组或本次新声明。原匹配只处理观点和证据身份。写入把临时观点编号换成正式编号，保留抽取的组归属。没有增加单独聚类调用。

**第二，身份引用的表示影响了回答。** 初版把本篇编号的字符串模式和已存编号枚举放在一个 anyOf 中。三个第二篇答复都写成重复的旧编号。换成接受同一组字符串的单一模式后，三份第二篇都给出了有效、不重复的引用。提示词没变，引用接受集合也没变。这个配对诊断说明表示影响了这三次输出，不足以认定提供方存在普遍缺陷；[官方文档](https://developers.openai.com/api/docs/guides/structured-outputs)将 anyOf 与 pattern 都列为支持项。

**第三，自己的校验过严。** 一个答复已经正确引用 Rubin，却额外声明了一个没有用到的新组。代码仅因这个声明就拒绝整篇。实际上，原流程会先筛掉没有被候选引用的声明，写入器也只创建有最终成员的组。这条拒绝没有保护任何实际产物。

现在只移除这条拒绝。空引用、重复引用、未声明的本篇编号、未展示的旧组编号仍拒绝；重复的新定义编号、空名称和范围仍拒绝。原答原样保存，没有自动去重、补填或手改成员。23 份未重复计数的主线抽取原答中，4 份有未用声明；3 份同时有重复引用，仍应拒绝；1 份仅被这条多余检查挡住。本次代码修复覆盖该 1/1 类。
