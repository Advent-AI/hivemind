# 第二阶段：先说明证据的作用，再决定是否新增问题

状态：D340 的研究提案。只读取既有回答、账本和代码；未改变生产规则、提示词、金标或默认模型，未发新模型请求。第一阶段的精确合同由独立子任务处理。

D341 深查后修订：旧 v29 已有独立理由字段和额外身份复核，仍发生低价值新建及关键条件被合并丢失。因此“正面说明新建价值”只是必要条件；工作顺序需改为整篇提炼业务更新、对比已有知识，再选去向。完整例子及对本提案的限制见 [分析师视角的 trace 复核](../2026-10-27-analyst-trace-review/review.md)。

来源拆分的实验范围仍是 D339 的三篇报道/分析文章。下文的“新问题需来源依据”适用于这类材料；用户自己写的投资备忘录仍保留 D59/D60 的例外，其判断可直接成为候选且可没有证据。本次不把报道规则推广到全部类别。

**核心问题是把三种不同判断混在一起：有无业务关系、是不是同一个问题、是否值得独立跟踪。** 分开两次模型调用只隔离了原文阅读，还没有解决这三种判断。

例如，CoreWeave 积压订单和上线容量可以说明 NVIDIA 下游需求及兑现限制；它们不是 NVIDIA 已确认收入，也不是 NVIDIA 已签融资担保。没有 CoreWeave 专属卡片，不代表这段信息无用；出现客户名字，也不代表必须新增客户卡片。

### 免费普查与一个完整例子

[census.py](census.py) 只读两个保存的账本及模型档案，输出 [更正后的逐候选记录](../../../poc/reports/2026-10-27-analyst-trace-review/census-corrected.json)。按 JSON 字段统计决定；有明确请求列表时，按其调用 ID、散列及完整 candidate state 找原答。无列表的旧记录保留原上界方法，不用关键词猜类。旧版错误地也对并发记录使用调用编号上界，漏掉部分已记录原答；[原结果](../../../poc/reports/2026-10-27-routing-design/census.json)作为历史保留。

| 保存的数据 | matching 记录 | 候选决定 | 新建 / 合并 | 精确找到最终新卡 | 唯一原答 / 多个不同原答 / 无原答匹配 |
|---|---:|---:|---:|---:|---:|
| 默认 v23 Jev，480 个输入的历史账本 | 250 | 102 | 95 / 7 | 90 | 93 / 1 / 8 |
| v29 NVDA 三个月研究账本，1,114 个输入 | 677 | 69 | 53 / 16 | 50 | 53 / 0 / 16 |

“精确找到”要求创建序号、输入 ID、问题全文同时相等。未找到不自动等于失败，也可能被合并或拒收。原答不唯一的样本不参加关系类别统计；空列表的初始候选可能根本不需要 Jev 请求。v29 更正后仍有 16 条无法完整关联，不为其补猜关系。两组语料、配置不同，90 比 50 不是优化效果。

默认 v23 中，23 个 `new` 有至少一个原答关系 `part_of`，22 个精确找到新卡；28 个 `new` 有 `same_matter_different_quantity`。类别可重叠。v29 更正后有 6 个 `new` 含 `part_of`，都找到新卡。这是**进入缺少独立价值判断路径的数量**，不是错误新增率。

正控例子：v23 record 2，seq 3，候选 c1 是 FY2027 Compute & Networking 分部收入。完整请求匹配原答 call 577；对总收入 v2 判 `part_of=0.97`，对 Data Center v3 判 `part_of=0.67`；决定仍是 `new`，checks 无拒收/未开/notes；写成 v9。证明“识别组成关系”不会触发任何“是否值得独立跟踪”的决策。此例不证明 v9 应被删除。

范围内的计算新增费用为 $0。本次不重算历史付费账单；原档案含不属于当前账本的调用，不能用整库费用冒充这 171 个候选的费用。

## 建议的第二阶段职责

逻辑顺序是：**整篇提炼重要业务更新及反证/限制 → 对照已有知识判断增量 → 优先更新已有问题，必要时提出新问题 → 确认身份并保留信息差异 → 写入。** 这些是不同决定，不等于强制新增五次模型调用。候选方案仍可用一次 routing 调用形成更新和目标提议，沿用后面的匹配/写入步骤；“研究更新”暂不定义为新的持久化对象。

### 1. 先看业务关系，不找“最像的一张卡”

输入是第一阶段确认的来源记录、原文位置和来源版本，以及同一 dispatch 序号下的目标问题上下文。routing 不修改来源摘要、日期、说话者或层级。需要更正来源时回到来源修订，旧关联不能继续套在新内容上。

每个合法目标必须带完整问题、解决条件及必要的对象/范围/期间说明。目标清单由代码生成一次，展示列表、schema 允许 ID、实际接受 ID 必须相同；只在 group 里显示的成员不再成为看得见却不能使用的目标。

每个关联说明一个具体作用：原文的什么事实，会改变该问题的什么判断。语义复核必须能从原文支持这条连接；“同公司”“同领域”“最近的收入指标”不成立。数值所属对象保持不变：客户订单不能加到 NVIDIA 收入，计划不能改成承诺。

一项更新可引用同篇多条来源，共享业务解释只写一次；不同来源的身份、日期、限制不因此合并。输入还需相关已有证据及其限制，才能判断这次增加了什么；只有问题标题不足以做到。这项上下文选择尚需实际验证，不能靠不断扩大列表代替。

优先挂最具体且合适的问题，但不强制只有一个：确实分别影响两个问题时，可以给两条独立理由。同一来源仍是同一来源，不能在最终判断中当两份独立证据。是否支持/反对最终结论由后续评判负责，routing 不先制造总分。

目标上下文也须带现有依赖关系：如果 B 通过 A 的结论获得这条信息，就按既有规则挂 A，不再通过直接关联给 B 重复一份。允许多个直接关联不等于允许绕过依赖重复计入。

业务驱动可进入结果问题，但不能任意跨时间：较早结果可以是基线，远期计划可以说明机制；若联系依赖未给出的订单归属或兑现时间，明确未解决。用一个时间截断规则会丢失有用背景，用“任何预测都可用”又会泛化过度。该语义边界必须拿真实正反例确认。

### 2. 新建必须有正面的理由

一个新问题提议引用一组来源记录，而不是每条记录各创建一张卡。它必须同时说明：

1. 需要跟踪的具体不确定性，以及其对研究对象的业务意义。
2. 已有问题为什么不能承接；只作为其中证据会失去什么独立判断。
3. 什么结果能回答它、何时评估；沿用现有问题类型及身份约束，不凭空捏造期限、指标或台阶。

没有已有目标只满足“当前无去向”，不满足以上三项。无法判断身份、找不到清单中的适当目标、代码拒绝某次合并，都不能自动补成新卡。若后续匹配发现已有同一问题，则用已有问题承接；不因提议已经生成就必须兑现新卡。

这沿用此前 admission 提案的业务重要性判断，不增加按公司数卡片的硬上限、固定重点公司清单或关键词门槛。模型写了 `why_independent` 也不代表理由正确；代码只能检查字段/引用齐全，价值仍须语义评测。

D341 已发现 v29 的 `lost_if_folded` 仍能用“可单独观察一个子集”自圆其说。需进一步检查：保持已有问题的判断不变，该新问题不同结果是否仍会显著改变一个业务情景，以及原文如何支持这种区别。不能把“数量不同”当充分条件，也不能为凑签约/收入格式把技术采用问题改写掉。

### 3. 未入库的内容有记录，但不制造另一个无限队列

每条来源记录必须得到一次明确处置。候选封闭集合：

| 处置 | 含义 | 目标要求 |
|---|---|---|
| `assigned` | 能说明对已有问题或本次新问题提议的作用 | 至少一个合法引用，每个引用有其理由 |
| `background` | 有业务内容，但本次没有独立跟踪必要或适当关联 | 无目标，简短理由 |
| `outside_scope` | 不属于此次研究范围或非业务正文 | 无目标，简短理由 |
| `unresolved` | 归属、关系、目标检索或新建理由不足，暂时无法判定 | 无目标，指明缺少什么 |

本表是待评审合同，不是已经上线的 JSON schema。精确字段名和旧 handover 的版本转换在决定采纳后固定。`assigned` 到提议不算已入库；每个提议还需记录最后合并、新建或拒收结果，其引用者不能被静默丢弃。

`background` 和 `unresolved` 留在来源/处理档案，不自动进入人工待办，也不每天重新尝试开卡。现有人工复核模块没有新增工作流授权。这样“保留阅读结果”和“无限累积待处理观点”是两件事。以后若需要回查，必须另行明确触发和范围。

### 4. 身份、重复与分组各做自己的工作

- 问题身份：同一对象、范围、问题及期间按现有规则合并；下一期间按现有接续规则处理。自由措辞仍交语义判断，不改成关键词等价。
- 来源身份：多篇转载同一次原始发言只能增加出处；新说话者的不同观点不能靠引文相同合并。保留 D339 的两个说话者正反例。
- 分组：同一现实事项的不同问题可属于同组；分到一起不等于问题重复，也不等于证据可以挂到组内所有卡片。
- 顺序：前一输入写入后，下一输入才能据此判断新颖性。并发准备若使用过期上下文，沿用现有顺序/失效规则，不把整天输入拿同一空库独立开卡。

## 边界表：采纳前必须实现及验证的要求

### 状态 × 事件

所有业务日期读来源记录或显式运行输入，排序读 dispatch 序号，不读墙上时钟。以下不新增存储事务或自动重试机制。

| 状态 | 事件 | 结果与记录 |
|---|---|---|
| 尚未关联 | 库为空 | 仍须正面提出重要新问题；空库不等于全建。背景及未解决有处置 |
| 尚未关联 | 已有合适问题 | 建关联计划，不改变来源；记录所用上下文序号 |
| 已有计划 | 确定是重复陈述/较新修订 | 交现有重复/替代判断，保留原始来源身份；不增加独立佐证数 |
| 已有提议 | 与现有问题同一 / 后续期间 / 包含 / 不同 / 不确定 | 前两项按原合并/接续条件；后面三项各需独立接纳理由，不默认新建 |
| 已有提议 | 键或对象冲突导致不能合并 | 记录冲突和未完成接纳，不以兜底分支开卡 |
| 已有计划 | 输出缺项、非法 ID、拒答、外部失败、再次失败 | 显式失败；不把失败当空结果。来源仍在。沿用既有失败/重试边界 |
| 已有计划 | 写到一半崩溃 / 结束时仍在途 | 沿用原事务、恢复及幂等机制；没有提交就不声称送达，不能重复开卡 |
| 已有计划 | 别的写者先提交 | 使用现有顺序校验；失效计划重新判断，不能按旧“找不到”直接建卡 |
| 已有计划 | 原文被纠正 / 配置改变 | 新来源或新配置版本；旧计划不可冒充新输入结果 |
| 已完成 | 下一天再报道同一事 / 两个研究范围同时使用 | 新的输入序号和明确范围；不改来源日，不把同一句复制成独立事实，不串用局部目标 ID |
| 已完成未入库 | 没有新事件 | 保持档案结果，不自动再试、不自动转人工队列 |

### 值 × 读者

| 值 | 写者 | 读者和要求 |
|---|---|---|
| 来源 ID、版本、引文、归属及时间 | 第一阶段/原文复制器 | routing、重复比较、证据写入、评判；都保持原意，时间回退另由来源合同审查 |
| 可选目标及上下文序号 | 库快照构建器 | 提示词、schema、关联校验、匹配；合法集合一致，组成员也不例外 |
| 每条来源的处置及关系理由 | routing | 转换器、研究测量、处理档案；不当成来源原话或评判结论 |
| 新问题提议及独立理由 | routing | 身份比较、接纳、候选写者；无法合并不能绕过接纳 |
| 真实目标 ID、重复/替代身份 | 现有匹配及 writer | 证据关联、分组、后续评判、UI；一个来源不能因多目标变成独立佐证 |
| 最终写入/合并/拒收状态 | writer/处理记录 | 统计及恢复；提议、合法回答和真实送达分别计数 |

### 新路径 × 旧检查

| 旧检查 | 新方案必须满足 |
|---|---|
| 原文位置、来源归属、时间 | 只引用第一阶段结果；禁止第二阶段偷偷修摘要 |
| 全部引用合法、每项有处置 | exact set 对齐；缺项、重复 ID、额外 ID 都失败，不靠数量相同蒙混 |
| 数量/事件、期间、对象范围、台阶与截止日 | 沿用当前限制；不把长期数量改叫事件绕过限制。此前 period/milestone 提案需独立决定 |
| 问题键冲突、既有问题、接续 | 继续检查；冲突改变该提议结果，不自动生成替代新卡 |
| 重复、替代、多个说话者 | 同一来源不能增权，不同陈述不能因引文一样丢失 |
| 分组和成员 | 沿用 D165/D166；不以创建组替代问题接纳，不无关扩散证据 |
| 顺序可见性、恢复、旧配置重放 | 必须跑真实调用入口；未更新旧档案含义，没有默默的新版本适配 |

### 既有决定的约束

检索了 D38、D51、D62、D149、D155、D164–D169、D171、D177、D338–D339，及既有 admission 提案。

- D155：**“清单是参考，先修身份，再按顺序验证归组”**。不得把参考清单收紧为选题硬门槛。
- D62 曾采用 **“the firm's total and largest-segment full-year numbers, every full-year number the firm guides, dated pending events”** 的稳定抽取配方，并规定 **“No cap on the number of views”**。去掉强制逐项开卡是对既有取舍的修订建议，不能只称为修一个未经授权的代码错误；不同时引入数量配额。
- D167 引 Alex：**“我不要 hardcode 解法 it's premature optimization, not general root fix, you need to make sure then poc then measure result”**。其明确拒绝的“同主题、同指标、同期间就合并”不能以降低卡数之名复活。
- D165：**“a company's own reported or guided financial lines ... belong to the company and carry no group unless the line itself tracks such a matter”**。新增接纳判断不能把财务卡统统塞成公司文件夹。
- D169 已采用 Jev；本提案不是静默切换匹配模型。先解决缺失的决策及测量，再测哪种配置能完成。
- D177 候选提示词仍未推广；v29 不等于默认库。本次不依据一个研究版本自动覆盖默认。
- D162 还限定 **“最终仍交现有证据、候选观点及归属，不增加产品数据层”**。来源档案的独立持久化若成为产品方案，会涉及这一边界；本轮仅保存研究产物，不视为已有生产存储授权。
- D38 的问题、结果台阶、截止日及 D51 无投票的边界保留。若要改成另一种长期投资论点对象，那是新的产品决定，不属于本次 routing 修订。

## 怎么证明改善，而不是让卡片变少

先确认语义标准，再付费。下一步是固定真实案例和预期行为，不马上再跑三个月。

1. **关联精准与召回一起算。** 每条候选关联都判断关系能否成立；同时数重要来源是否送达。加入融资担保、收入、EPS、需求、供给限制、未解决等不同去向，不能再全是 `v6`。全挂一张卡、全不挂两种简单程序都必须失败。
2. **新问题接纳独立计分。** 加入应该独立的新问题、已有问题的补充证据、同题不同表述、实际不同人口范围、新期间、同组不同问题、未知身份。不能把“卡片少”当准确，把“没有任何新增”当成功。
3. **从原文一直验到最终库。** 原文陈述、关联计划、身份决定、重复比较、最终目标逐层对照。单测 `sift` 不再冒充入库验证；来源归属错误的样本不能拿来只评 routing。
4. **同一报道多次出现，卡片及佐证数不应乱涨。** 用原档案中的转载和同话换述验证；再加同组真正新问题作为正控，防止一律合并。按新独立问题/报道次数分别看增长，而不只看总数。
5. **模型控制。** 在固定开发集上原方案和候选方案各至少三次独立新回答；先量旧方案对自己的差异，不跨回答投票，不改金标追分。测试集只对最终配置评分一次。错误原因报告到每条原始记录。

本次还没有人工确认的均衡关联/接纳金标，不能给出“能减少多少误建”的百分比。阻止默认新建可覆盖这个控制分支，但不等于语义错误全部消失；错误独立理由、漏检目标、错误来源仍会让它出错。

**规模与速度约束：** 下一 POC 不默认每条来源再发一个调用；先以每输入一次 routing 计划为候选，真实后续匹配成本另计。记录目标数、来源数、输入/输出 tokens、模型次数、总费用、端到端耗时和卡片增长。旧 D339 分步已比原方案慢且贵；任何新增调用或扩大上下文必须给出具体收益和预算，不能只报正确率。实际 token 和延时需要运行才能测，不以字符数猜测。当前付费预算为 0；新实验的范围、规模和费用上限在标准确定后单独写出。

## 建议先改什么

建议优先固定分析师所需的输出：**重要业务更新、其关键依据/反证/限制，以及相对已有知识的增量。** 再用这种输出决定更新哪一个问题或是否新建。禁止匹配失败自动新建仍必要，但单独采用这条规则或增加理由字段不够；只堵 writer，会把不断生成的低价值候选搬成另一堆未处理记录。

这项选择会改变哪些问题进入库，需要 Alex 确认上述真实例子的判法后，才固定 schema、写生产代码及开新付费实验。目前完成的是可复查的诊断和候选设计，尚未证明优化效果。
