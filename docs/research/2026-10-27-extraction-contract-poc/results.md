# 抽取与处理流程：完成结果

**主要问题确实包含我设计的接入和处理机制，不能归结为模型随机。** 分开读原文与选去向，改善了这三篇开发文章的内容保留；但关联判断、来源时间、同句合并以及我的测试指标仍有问题。没有达到生产推广条件。

例子：CoreWeave 的 1,040 亿美元积压订单在 DeepSeek 三次分步来源记录里都有。一次有效关联回答把它留待处理，另一次也留待处理，第三次关联回答格式坏了。内容没有在第一步消失。换成“模型没读到”去改阅读 prompt，会修错地方。

## 我的指标也需要被质疑

全部 **31/31 标签、18/18 核心标签** 的 `required_primary_link` 都是 `v6`。一个把所有内容都挂到 Data Center revenue 的固定程序，也能满足这些目标编号。因此上表能衡量这些正例是否送达，**不能单独衡量关联是否有区分能力**。

已有排除标签和人工复核能揭露部分多抽、错挂，但未覆盖所有额外记录的正确去向。此次没有事后改标签，也没有再开一轮模型试验。下一轮关联验证必须先明确不同去向、应待处理、应忽略的真实案例，尤其同时包含业务驱动、财务结果和仅字面相似的事项；这需要先确认测量标准。

另外两类旧计分错误已在人工复核中纠正：030 的引文含竞争段落，但摘要未保留竞争机制，不能算；009/e9、035/e10 在另一句保留训练与推理的差异，应按原意计入，不能仅因没有命中原锚点判漏。所有 706 条原始摘要已阅读；[标注脚本](finalize.py) 对 36 个样本逐条指定 31 类陈述所需记录，生成 1,116 个阶段判定。额外记录的已见问题如下，不宣称它们已有完整独立金标。

## 更合理的处理边界

我的旧做法把“来源说了什么”“它说明哪一个业务变化”“它要进入哪个问题”“是否和旧记录相同”挤在一起。分成两次模型调用只拆开前两部分，尚未把整条路径设计完整。

以 CoreWeave 为例，来源是“客户积压订单多、已上线容量少”。这既可能支持 GPU 需求，也可能说明供电限制使需求延后兑现。它不是 NVIDIA 已确认收入，更不是 NVIDIA 已签担保。好的流程应保留来源陈述，再说明它对哪个问题有什么帮助，而不是把客户数值改成 NVIDIA 数值，或按几个共同词选择问题。

以下是供下一步选定的结构规则，不是本次偷偷扩建的产品：

| 要解决的事 | 一个归属明确的规则 |
|---|---|
| 避免关联失败抹掉已读内容 | 来源陈述只由原文决定；关联结果引用它，不改写它。尚无去向的陈述保留明确状态。来源层的研究记录不冒充已接纳的库证据。 |
| 避免漏项与坏编号 | 程序复制原文位置；每个已抽取陈述有一个明确处置；展示、schema 与接受的目标集合相同。逐段回答只查结构，不证明内容完整。 |
| 避免主题相似被当成业务关系 | 关联负责说明该陈述怎样改变问题的判断；没有可辩护的关系就明确无合适去向。下一轮用不同去向和反例验证，不能只用全是 `v6` 的正例。 |
| 避免去重毁掉内容 | 相同出处可以承载不同事实；只有认定同一陈述才合并来源。引用相同不能删除第二个摘要或说话者。 |
| 避免虚构时间影响后续比较 | 报道日、原发言日、事件期间各自保留；未知就是未知，任何归一化都要有来源依据。只修抽取字段不足以证明写入后仍保留这一含义。 |

优先完成第一条与第四条的交接设计：**每个已读陈述在每个处理边界都有可追踪的去向，不能因为没关联或共用引文而无声消失。** 它解决已经数清的丢失；不声称能自动解决模型遗漏、错误业务判断或模糊时间。

真实库的匹配与评判依赖摘要和来源时间；例如 `views/jev_matching.py`、`views/writing.py` 当前还会用报道日替代空的原发言日。这是本 POC 边界外的既有消费者，不在本次改动或全面审核范围内。它说明：本轮来源层的空日期保留，不能当成端到端时间含义已修好的证据。重新设计需把这些读者纳入合同，而不能再只测第一步。

## 成本与速度

| 配置（每组 9 个独立样本） | 估算费用 | 输入 tokens | 输出 tokens | 样本模型步骤时间中位数 |
|---|---:|---:|---:|---:|
| Luna 原流程 | $0.007520 | 50,289 | 11,762 | 13.92 秒 |
| Luna 分步 | $0.029026 | 109,035 | 41,092 | 57.53 秒 |
| DeepSeek 原流程 | $0.024799 | 58,596 | 16,428 | 6.90 秒 |
| DeepSeek 分步 | $0.092517 | 155,694 | 55,108 | 25.68 秒 |

每篇的三个耗时与逐步 usage 在最终 JSON 中。分步是两次模型步骤耗时相加；修复的来源耗时取原失败记录，含少量本地处理，属于近似值。它不包含分两次会话补关联之间的等待，不能称连续产品端到端耗时。

原系统 prompt 7,458 字符；来源 prompt 1,998，关联 prompt 1,243，共 3,241。**文字变少，实际输入和输出却变多**：逐段 schema、逐条来源字段和第二步重传记录都增加成本。没有单独可靠的 system-prompt token 计数；上表用供应商返回的完整请求 token，不能把字符量当 token。逐段必答的收益是可查处置，代价是来源层大量细碎记录；当前 POC 不能当作已经优化的生产格式。

## 验证与明确边界

`finish.py checks` 用真实坏答 010 和好答 007 顺序处理：坏答后仍完成好答；恢复错误停止分支的代码变异会失败。真实临时 SQLite 同时证明传输失败仍停止。付费前冻结 preflight 与上次日志逐字相同：4,217 项、772 次历史拒收；没有声称这些旧问题消失。

`mechanics_proof.py` 检查 36 个结果、1,116 个阶段判定、9 条原始分包响应和 544 条送检记录；空选择却计分的代码变异被明确断言抓到。完整套件和文档检查由 [refresh](refresh.md) 记录。
