# Existing-evidence lane: code assigns unique local evidence IDs

## Observed class and mechanism

In the completed 60-call comparison, 1 of 30 changed-B answers and 0 of 30 control-B answers repeated an evidence ID. The affected answer is `gnews:8f8a2d115ab834c7026aefd1`, treatment draw 3: all 14 distinct evidence records used the exact article ID as their local `id`. All 14 survived the extraction handover. This is one observed answer, not a general defect rate or proof the field-description edit caused it.

The schema only says `id` is a string. The actual downstream `matching.build_lists` keys matches by `(evidence id, existing view id)`, and `writing._write` also keys checked decisions and returned IDs by the evidence ID. Replaying the **stored handover** with the actual matching-list builder on a read-only copy of the prior research library yields 14 evidence-to-view links but only 3 distinct matching lookup keys. On an otherwise identical copy whose 14 evidence records receive distinct local IDs before the existing sift, it yields 14 distinct keys. Neither replay called a matcher, wrote to the library or proves how many facts would have reached a reader in production. All source quotes and existing question links remained unchanged.

## One structural rule

B returns only evidence for already existing questions, and its answer has no candidates that refer to an evidence ID. Therefore, in the isolated B adapter, code assigns each source answer evidence a unique local identifier based on its **position in that immutable answer**: `e1`, `e2`, … before the existing sift. Keep raw model IDs and the raw response separately, plus a mapping of `(answer identity, original index, original ID, assigned ID)` for review. Do this for every B response, not just repeated IDs or this article. The identifier's scope is one article, one lane, one exact answer; across lanes or draws, retain that scope explicitly. A duplicate quote still follows the unchanged existing within-answer quote merge. A model's meaning, source, quote, time, tier and chosen question links are not changed. This is code-owned identity, not a relevance or importance decision. Never apply this blindly to A: A candidates refer to their answer's evidence IDs, and a duplicate there makes the relationship ambiguous.

## Readers, events and old checks

Raw response → B local-ID adapter → original `sift_with_groups` → `file_reading` → hypothetical matching lookup → actual later matcher/writer (not exercised by this POC). Each reader still receives the same schema fields and question IDs; archives and raw-answer reviews keep the original IDs. Input article and ledger snapshots are read-only. Repeating the adapter on an unchanged stored answer yields the same mapping; a different answer has a different answer identity. Quote refusal, duplicate-quote handling, invalid existing ID, parent narrowing and no-home handling stay in their original locations and must still work. Failure of the adapter or missing fields refuses the item; it cannot become an empty success. Failure of one concurrent lane marks the pair incomplete. No stored historical answer is modified.

Before writing the adapter, independent design review. Then run on **all 60 stored raw B answers**: show original-vs-new handovers have the same ordered source quotes, summaries, attribution, tiers, periods and destination question IDs, except local IDs and ID-bearing drop messages. Census how many would be affected and whether any duplicate-quote merge, wrong-source refusal or no-home outcome changes. Exercise the actual matcher lookup on the decisive affected case before and after. Positive control with distinct original IDs, duplicate-ID counterexample, a no-home item, invalid quote and same-quote repeated item; changing source, question link or semantic judgment is a test failure. The accepted ID mapping must match a written raw-answer hash. A mutation that leaves repeated IDs must fail the uniqueness/lookup assertion. Preserve all original results and metrics without retroactive correction.

The next live comparison must identify whether it uses this adapter, because it changes handover identity even though model bytes are unchanged. An offline replay proves this code's behavior for stored decisions; it does not prove model quality or end-to-end writer delivery. Production code and frozen gold are untouched.

## Review: B-local numbering alone cannot join the two lanes

The independent reviewer confirmed the stored 14-record/3-key mechanism but found a serious missing boundary: A may already have `e1`, so writing B's `e1` beside it without changing the actual IDs seen by matcher/writer collides. A's candidate also refers to A evidence by local ID. Merely adding a lane label for a report does not protect the actual matcher/writer. The standalone B normalization proposal is therefore not built or sent downstream as a completed solution.

The next design must explicitly allocate unique IDs across the joined answer after each lane has been checked, map every A candidate evidence reference to its own evidence's new ID, and preserve the raw-answer hash and both lane-local identities. An A answer with duplicate local evidence IDs cannot be safely rewritten when its candidate references are ambiguous and must be refused, not guessed. In B, which has no candidate-to-evidence references, code may safely assign unique temporary local IDs by source-array position before sift. Existing quote checks can repair quotations, narrow links, reject no-home or merge same-quote records; the comparison is **post-check equivalence**, not a promise the handover always equals raw text.

The actual existing matcher and writer must be replayed on a scratch ledger for at least: A and B both have original `e1` but different sources/destinations; A's candidate matches an existing question; A's candidate is rejected; the same quotation appears in both lanes with distinct destinations. Candidate-to-evidence references must remain on A's actual source record, not B's. Same-quote records are not automatically treated as independent confirmation or semantically merged; there is currently no tested cross-lane deduplication policy. Report that gap rather than claiming joined production delivery or silently adding a one-off merge rule. Refusal of either lane yields an incomplete item and preserves raw responses.
