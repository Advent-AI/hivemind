The product checks that a forecast cites real evidence, but it never checks what the cited numbers measure, how they were combined, or whether related answers can both be true. On September 20, one judge put NVIDIA’s Q4 Data Center revenue at **$146B** while another put **the entire company at $127B**. Both answers passed. The same design lets one judge add two commitments whose overlap is unknown, turn a five-company spending forecast into a four-company estimate using an unrelated ratio, or call yesterday’s forecast the market’s view. I would keep the investment questions separate and have related answers use one shared, source-backed calculation. The model would still decide what the evidence implies. Code would check what each number refers to, recalculate the arithmetic, and catch contradictions before publication.

## The fix I would choose and the test that could refute it

**Give each published number a calculation a reader can follow, and reuse the same inputs across answers that share them.**

- **Extraction and writing** would keep the quote and identify any figure used in a calculation by its source, company or population, measure, period, units, and what kind of number it is, such as a reported result, guidance, or an estimate. Keep one evidence record. Related forecasts can refer to the same numeric input without copying the article into every question.
- **Matching** would identify specific relationships such as *this segment belongs to this total*, *these estimates use the same prior-year base*, or *the relationship is unresolved*. The model can interpret ambiguous source language. Code can verify declared identities and apply known accounting relationships. Identical dollar values alone establish nothing.
- **Judging and publication** would use the same dated inputs for a related group of forecasts. Each answer would identify its external comparison, if available, and show the inputs, calculations, and assumptions that drive its forecast. Code would recompute the math and check known relationships, including part versus whole and the same growth rate applied to the same base. The model would decide which signals matter, what to discount, and when the evidence supports only a broad range or a conditional scenario. A guess about overlap or a haircut could still be discussed. It would stay visibly an assumption and could not pass for a sourced increment. A failed reconciliation would be visible as unresolved rather than publishing two incompatible updates together.

This matches the frozen gold’s reasoning. **q02** derives a segment comparison from an outside total and a sourced mix, then uses **q01**’s total forecast to reason about the segment. **q22** reuses q01’s FY2027 base for FY2028. **q19** discounts the CPU target using the selling window and what the target would require in units. **q01** considers the CPU target as an upside driver without assigning it a fixed increment. Those are legitimate analyst inferences. The proposed checks preserve them while making their provenance and assumptions visible. [Frozen judgement gold](/Users/lchingen/hivemind/docs/research/2026-11-01-e2e-loop/judgement-gold/gold-v1.json), [Frozen judgement standard](/Users/lchingen/hivemind/docs/research/2026-11-01-e2e-loop/judgement-gold/ruler-v1.md:18)

**Cheapest refuting test, $0.** Reconstruct the published calculations by hand from the archived requests above, using the same proposed rules on the frozen q02, q19, and q22 examples as controls. The decisive check is already visible: with Data Center at $164B through Q2 and about $100B in Q3, a company-wide Q4 of $127B caps that particular annual segment calculation at **about $391B**. To reach $410B, the analyst must revise a stated input or show a different scenario. Stop the design if it admits the incompatible pair, treats unknown overlap as an additive fact, or lets an unsupported adjustment cross a boundary simply by labelling it an assumption. Also stop if it rejects the gold’s valid share, base-year, or execution-risk reasoning. This test establishes whether the representation can express and check the right distinctions. It does not measure how often a future model would use it correctly.
