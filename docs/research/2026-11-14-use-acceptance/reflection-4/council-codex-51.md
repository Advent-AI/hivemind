**No-go: the design needs a complete live-store contract before code.** WAL is a plausible way to let the writer commit during a read, but the current design does not yet establish that the deployed readers can open, preserve and safely copy that store.

1. **The working rule is broader than the design says.** [AGENTS.md §9](/Users/lchingen/hivemind/AGENTS.md:431) says, “Never open a live run’s databases,” and directs readers to a snapshot. It does not limit that rule to production’s rollback-journal stores. The proposed live reads are therefore a departure that needs to be explicitly reconciled and decided, not described as leaving the rule in force only for production.

2. **WAL files and permissions need a contract and proof.** A live WAL database is not just `views.sqlite`: readers need access to its current WAL and shared-memory state, and a copied main file alone may omit committed data. Specify the actual host and container mounts, directory permissions, first-open and restart behaviour, and how completed stores are copied or snapshotted. Test a fresh read-only connection while committed data is still in the WAL, including the intended read-only mount. The current reader opens `mode=ro`; the design does not yet prove that deployment path. [store.py](/Users/lchingen/hivemind/src/hivemind/views/store.py:216), [service operation](/Users/lchingen/hivemind/docs/poc/service.md:68)

3. **Bound long reads and checkpoint effects.** The streamed Idea route can hold a snapshot across model calls. WAL permits commits during ordinary reads, but a long-lived reader can delay checkpoint progress and grow the WAL; “readers never block the writer” is too absolute as an operating claim. Specify transaction lifetime, disconnect and error cleanup, checkpoint ownership, growth/space limits and what happens on a failed checkpoint or restart. Test a held reader across commits and checkpointing, then release it and verify recovery. [DESIGN.md](/Users/lchingen/hivemind/docs/research/2026-11-14-use-acceptance/live-service/DESIGN.md:7)

4. **Set the date rule for explicit reads.** The table says later in-progress days remain outside `/library`, but the proposed readiness check only rejects the *first* unfinished day; it does not say what happens when a caller supplies an `as_of` in a later unfinished day. Decide whether to reject, cap, or intentionally allow that explicit read, and apply the same rule to history, changes, search and MCP. Test both default and explicit dates. [DESIGN.md](/Users/lchingen/hivemind/docs/research/2026-11-14-use-acceptance/live-service/DESIGN.md:30)

5. **Finish the reader and proof inventory.** MCP currently holds a shared connection and builds server instructions at startup; “compute the object list per call” needs to say where that changing list is returned and how concurrent tool calls get independent snapshots. HTTP startup’s index build also opens the ledger outside an ordinary request. Account for direct tools and scripts that open or copy `views.sqlite`, including preflight and mock exports. The extension proof compares selected database rows and request records, **not the judge store byte for byte**; re-run it and check the broader storage/copy contract separately. [MCP](/Users/lchingen/hivemind/scripts/hivemind_mcp.py:29), [API startup](/Users/lchingen/hivemind/scripts/hivemind_api.py:231), [extension proof](/Users/lchingen/hivemind/docs/research/2026-11-14-use-acceptance/carried-run/extension_proof.py:219)

It should not be presented as a reason to leave a live first-day leak or an unidentified stale snapshot in the production path; the proposed wording can be shown to Alex with the operating choice and evidence.

CONSENSUS: no, because live database access, WAL sidecars and lifecycle, explicit-date reads, and all reader boundaries are not yet specified or proved.
