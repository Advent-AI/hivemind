**Not yet: version 3 closes several gaps, but the search path can still let an unfinished day change an answer for a completed day.** I would revise the contract before building the proof.

1. **Lexical search also needs the date boundary.** The contract limits which views are sent for embeddings, but the existing lexical search ranks the entire `views_fts` table and takes its first 50 hits before the service filters candidates by date. Views from an unfinished day can therefore crowd completed-day views out of those 50 or change their ranks; a search at the last completed day can differ from the same search on that day’s backup. This is an inference from the code, not a reproduced run. Specify visibility *before* the limit and ranking, then test a paused or crashed writer with enough matching unfinished views to affect the results. [Search]( /Users/lchingen/hivemind/src/hivemind/search.py:230), [FTS query](/Users/lchingen/hivemind/src/hivemind/views/store.py:325), [contract, rows 4a and 6](/Users/lchingen/hivemind/docs/research/2026-11-14-use-acceptance/live-service/OPERATING-CONTRACT.md:62).

2. **The checkpoint policy does not establish the stated size bound.** It checks after completed days. An unfinished day can continue writing or crash before the next check, and a day’s write volume is not bounded in the contract. The three-failure rule bounds the *number of completed days before stopping*, not WAL bytes or growth in an unfinished day. State the actual guarantee and the disk-exhaustion behavior; if a byte or free-space bound is required, specify how it is enforced during a day and test that case. [Contract, row 5](/Users/lchingen/hivemind/docs/research/2026-11-14-use-acceptance/live-service/OPERATING-CONTRACT.md:70).

3. **Preflight’s proposed copy conflicts with the stated authority.** A backup made *from* the live database still opens that database. Section 9 currently says never to open a live run’s databases, and proposed P1 permits the API and MCP service readers, while other users consume a snapshot. Row 7 instead permits preflight to open a live source without distinguishing it. Define who is authorized to create the snapshot and require preflight to receive that snapshot, or explicitly include the other behavior in the decision for Alex; a consistent SQLite copy alone does not settle the permission. [AGENTS §9](/Users/lchingen/hivemind/AGENTS.md:431), [contract, rows 7–8](/Users/lchingen/hivemind/docs/research/2026-11-14-use-acceptance/live-service/OPERATING-CONTRACT.md:87).

4. **Index refresh needs a failure and publication rule.** The current index builder commits each batch and can stop after a later batch fails. Version 3 says the index records its day, but does not say when that day advances, what search uses after a partial refresh, or how a request gets a consistent index and ledger state. Specify those states and test a failure after one successful batch, followed by a retry. [Index builder](/Users/lchingen/hivemind/src/hivemind/search.py:82), [contract, row 4a](/Users/lchingen/hivemind/docs/research/2026-11-14-use-acceptance/live-service/OPERATING-CONTRACT.md:62).

5. **MCP transaction ownership needs a concurrency case.** MCP currently shares one `LEDGER` connection for the process and supports streamable HTTP. The proposed transaction per tool call needs either a separate connection per concurrent call or an explicit serialization rule; the current proof only checks that no transaction remains *between* calls. Test overlapping calls across a writer commit, including cleanup on failure. [MCP entry point](/Users/lchingen/hivemind/scripts/hivemind_mcp.py:25), [contract, row 2](/Users/lchingen/hivemind/docs/research/2026-11-14-use-acceptance/live-service/OPERATING-CONTRACT.md:43).

The single bound resolver is the right direction, and P1 remains explicitly proposed. The proof should also retain the stated legacy and empty-store behavior when that resolver is introduced.

CONSENSUS: no, because the lexical search can still be influenced by unfinished work, and the checkpoint, copy authority, index-failure and concurrent MCP contracts need to be settled before the proof build.
