**Not yet. Version 4 addresses the five findings in principle, but the lexical-search rule may still fail its own backup comparison, and the copy and disk proofs need sharper contracts.**

1. **Filtering before the lexical limit is not necessarily enough.** The existing FTS query orders by SQLite’s `rank`. Even if the query restricts returned rows to visible views before `LIMIT`, FTS ranking can use statistics for the whole index, including unfinished views. Those views could therefore change the relative rank of visible results. The proposed paused-writer proof is the right test, but the design must say how ranking uses only the visible corpus—or explicitly accept a different ranking contract—before claiming equality with the completed-day backup. This is a code-based concern, not a reproduced failure. [Contract](/Users/lchingen/hivemind/docs/research/2026-11-14-use-acceptance/live-service/OPERATING-CONTRACT.md:64), [current FTS query](/Users/lchingen/hivemind/src/hivemind/views/store.py:325).

2. **The preflight acceptance rule needs an enforceable identity.** “Under `snapshots/`” and “a recorded final outcome” do not by themselves establish that the particular input is the snapshot created by the run’s script or the store belonging to a finished attempt. Define how the accepted path is tied to its run and attempt, how a snapshot is identified, and what happens to older standalone stores without those records. Test a live store placed or linked under a snapshot path, a stale or unrelated outcome, and the historical inputs preflight must continue to accept. The current launcher records outcomes by attempt folder in `run.json`; preflight presently accepts paths directly. [Contract](/Users/lchingen/hivemind/docs/research/2026-11-14-use-acceptance/live-service/OPERATING-CONTRACT.md:104), [launcher](/Users/lchingen/hivemind/clean-arch/step4-2026-11-10/stage_b/run_stage_b.py:85), [preflight](/Users/lchingen/hivemind/scripts/preflight.py:183).

3. **The full-disk test is narrower than the claim.** `max_page_count` can exercise a database-full error, but it does not establish behavior when the filesystem fills while extending the WAL or creating a side file. The contract should distinguish that test from an actual filesystem-full test, and specify what happens if recording the stop reason also fails for lack of space. [Contract, disk and proof](/Users/lchingen/hivemind/docs/research/2026-11-14-use-acceptance/live-service/OPERATING-CONTRACT.md:83).

4. **A resumed index refresh must be tied to its source.** Staged batches need an identity for the target completed day and the texts they represent. Otherwise, a retry after another day completes or after the served store is replaced could publish a mixture while advancing one day. State whether it resumes the original snapshot or discards and rebuilds the staging work, and test that transition.
