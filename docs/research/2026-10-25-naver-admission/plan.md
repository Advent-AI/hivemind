Alex explicitly asked to modify the extraction and validate this one case. D176's criterion is material information coverage and correct question attachment, not a required number of project cards. This is one frozen experiment arm; no schema, horizon policy, matching, writer, concurrency or working-database change.

## Inputs and proposed change

Read the full NAVER announcement from D174's preserved input copy. Reconstruct the exact pre-NAVER library from D174 control-1 strictly before sequence 22, excluding unordered audit rows. It contains the actual two SK questions produced by that control and the old library, but no NAVER or blog processing. Verify the reconstructed v23 request equals D174's failed NAVER request before paying.

The treatment uses `role-proposed.txt` as version 11, with category content copied unchanged and a test-only Config selecting T6-v11. Control uses the existing v23 Config. The complete request must differ only in the system message. Both use the same `gpt-6-luna` model, reasoning, output limit, user message and JSON schema.

The proposed role removes the automatic annual-number recipe, asks for a material uncovered business question, distinguishes annual measurement from a source-defined milestone with a numeric completion target, and retains source status. It names no company, project or capacity value. No other source category is activated on the new role. The existing year check still applies to annual metrics.

## Fixed measurement

Run three fresh controls and three fresh treatments, in order C1, T1, T2, C2, C3, T3. Each uses a new copy of one baseline and a new empty archive. Run the normal single-item dispatch → extraction → matching → writing path (`round.run`), at sequence 22. This test does not run daily judging or claim full-day performance. Every physical request uses the existing guarded single-attempt transport, with one outbound call at a time, a new $0.60 ceiling and maximum 36 calls across all six trials. Do not reuse the halted D174 journal. No network retries or adaptive second treatment.

Before calls, perform ordinary preflight on copies plus replay the recorded failed answer through the new version's unchanged code/schema checks. This should still reproduce the old refusal: the experiment changes what the model writes, not what code secretly permits. Audit the full system/user/schema request and record characters. Report actual prompt-token usage from the provider for each sample, not a character/token guess.

For this frozen pre-NAVER context, no existing thesis covers the GAK Sejong expansion: SK's factory, Rubin production and broad revenue are different questions. Success therefore requires retained source-grounded NAVER information under a legitimate new project question; in a different context a direct existing-question attachment could also be correct. This conditional expectation does not restore a universal project-card rule.

Read every raw answer, check result and final write. Report separately:

- retained announced expansion, 200 MW target and 2028 timing, across the quote, summary and question;
- source faithfully remains a plan, with no asserted funding, purchase order, delivery or revenue not stated in the source;
- an admissible project milestone rather than an out-of-range annual capacity forecast;
- no merge or evidence attachment to the SK project, Rubin production question or generic revenue solely because they share NVIDIA;
- valid existing/new group association under its scope; no mandatory group name/count;
- extra questions, source drops and any unsupported claims.

Report each of the six samples and control-versus-control variation. Treatment 3/3 success with failing controls supports this case only. If controls also succeed, say that the prior failure was not consistently reproduced. If treatment fails, preserve the result and do not tune another arm. This does not establish broad extraction quality or authorize promotion of T6-v11 as the default.
