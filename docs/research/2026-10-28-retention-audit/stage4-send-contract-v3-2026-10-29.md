# 五案例对照：发送与记录约定

2026-10-29。只修 [第一次发送程序审查](stage4-send-review-2026-10-29.txt)指出的六类问题；保留旧程序和试算，不改模型材料或评价参考。用户请求一次隔离对照，两个模型各 5 案 × 3 次；全部请求预留在每次实验 $0.60 内，预留是估计而非供应商账单上限。

| 状态 | 事件 | 结果 |
|---|---|---|
| 未发送 | 完整输入、固定计划、逐项预留通过，抢占唯一锁成功 | 固定内存中的请求与清单，准备发送；一次预留含最多 8 个在途请求 |
| 未发送 | 检查失败、重复启动、锁已存在 | 不发送；原记录保留 |
| 待发送 | 某个工作开始 | 在请求前独占创建并同步该次尝试记录；相同案例、模型、次数无法再启动 |
| 请求中 | 完成且有原始回答 | 原答先保存；再独立记录服务停止状态、JSON/schema/编号是否有效及用量。自然结束不等于内容有效 |
| 请求中 | 网络失败、缺失用量、超出估算 | 按整次预留记未知，停止安排新请求，等待已经在途的请求并记录；不重试 |
| 任意时点 | 程序崩溃 | 锁和已写尝试记录仍在；不自动重启或重发；没有回答的尝试标未知，由人核对服务商账单 |
| 全部结束 | 输出记录与清单 | 写完成清单；逐条解释、事实判断由后续人工模型阅读，不按格式给投资分 |

逐请求预留重新从 token 计数、请求字节、固定输出额度及对应费率计算；缺输入或输出 token 均不是零，停止后续调度。发送前从源资料重新构造实际请求，与已审查文件按序列化字节比较；发送时只使用已核实的内存副本，避免验证后换文件或调整 JSON 键序。模型输出保留供应商原始响应，解析出错也不丢原答；编号检查区分新目标、本篇其他材料和旧材料。一个程序一次持有锁，已发送的请求不通过缓存或重试代替新样本。

离线验证至少覆盖：原请求通过、换 JSON 键序被捕获；改变输入或输出预留后不通过；缺输入或输出用量停止；自然结束但坏 JSON 不算有效；收到的异常形状仍保留原答；同一尝试或第二个工作者无法重复发送。所有负对照先在临时目录及内存中执行，不连接供应商。费用校验、所有写入和输入准备的脚本均冻结哈希；一个已锁定的旧结果不能被覆盖。


后续审查发现三类遗漏：[审查记录](stage4-send-review-v2-2026-10-29.txt)。网络原始字节必须在 JSON 解码前保存；不是对象的合法 JSON 也必须写汇总；所有影响请求、费用和响应的实际依赖（阶段提示脚本、准备脚本、读取/构造数据的代码及提示、两个凭证与计数辅助脚本、配置和测试输入）在预留时记录摘要，启动和发送前重验。预留及启动程序使用独占记录，保留先前试算不覆盖。


第三次复核指出：[记录](stage4-send-review-v3-2026-10-29.txt) 一是服务错误即使附带用量也必须停止新请求；二是在导入依赖前和导入后各核对依赖摘要，计数结束再核对同一摘要，确保登记的代码就是完成计数的代码。
