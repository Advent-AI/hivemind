# 单篇抽取探针：收入增长和客户支出

2026-10-29，发送前登记。Alex 请求快速试 DeepSeek。前一轮只试评委，不能回答产品抽取；此处只测已发现抽取问题的一个实际步骤，不跑整条流程、不切默认模型。

**假设：**在同一篇文章及同一套抽取要求下，DeepSeek 可能更完整地理解相邻句的上下文。直接用 v38 的真实文章 64：华尔街收入增长 82%／41% 原文前句说是收入，但 v38 原回答 e2 写“指标不明”。同篇管理层对云厂商 2026 年 $6500 亿、2027 年超 $1 万亿支出预测是另一条对照。Alex 明确将这两条都判为核心；FY2028 EPS 可以留，未指定权重，不算垃圾或标签对错。文章中的股价、仓位、估值算术沿用既有原文标准，人工阅读，不能把其它未预设输出一概计垃圾。

**实际输入：**先用当前生产的 `extraction.request_for` 和 `model.build_request` 从原始条目、v38 配置和生产 universe 重建，验证 `model.request_identity` 与历史 v38 归档 call 209 的摘要完全一致；真实发送按生产构建的字典及 schema 字段次序，不使用归档排序后的 JSON。三个新鲜 `gpt-6-luna` 对照使用生产 Chat Completions 请求原样，三个 `deepseek-flash` 实验用同一 system、user 和 schema，通过 DeepSeek Responses API 的对应格式、8,000 输出上限与思考模式。DeepSeek 不支持同一个 Chat Completions JSON schema 接口，故协议外壳不同；即使其结果好，也不能将差别全归因于模型，且只代表此篇开发案例。六次都独立发送，不用缓存重放当样本。

**先固定的判断：**每次先检查请求、输出状态和 JSON 结构，再走生产 `sift_with_groups`（v22、保留未链接）核实引文和候选拒绝。对每个用户确认的核心事实，分别审完整信息、原文出处、谁说、是预测还是事实、两个期间、引文支持；一条或多条共同保留均可，漏关键部分计部分，不因碰到其中一个数字就算完整。每次只给两项完整／部分／没写和理由，不将空回答、失败或未通过检查算通过。未判定内容和可留 EPS 单列；误引原文、胡编、与投资无关的股价算术单列，并逐条人工核对。归档、查重和最终页面不在试验范围，不能声称最终留存改善。

**预算与范围：**最多六次请求、每次 8,000 输出 token、无自动重试、180 秒超时、8 线程。先计算 GPT 的实际输入 token 和 DeepSeek 官方 tokenizer 估算，分别按最大未缓存输入和输出价格、同时预留全部六次；连同计数请求保守预留不超过现有 $0.60，否则不发送。先跑修复后的存档预检，已知的历史状态假拒绝和四个不匹配请求单列，不将其误认为产品故障。用户已明确要求试 DeepSeek，D62 保留当前默认的决定不变；此探针不改变产品。

[只读复核](deepseek-extraction-probe-independent-review-2026-10-29.txt)指出预算尚未覆盖估算误差、上限多报和用量未知。统一按更保守的预留处理：每家输入上限取「官方计数或 tokenizer 估算的三倍」与「待发送请求 UTF-8 字节数的两倍」的较大者，再加 16,384 token 协议余量；每次输出预算按 8,064 token 计，实际请求上限仍为 8,000。GPT 的计数接口按一次同样输入另行预留。按 [OpenAI 标准价](https://developers.openai.com/api/docs/pricing) `gpt-6-luna` 每百万输入 $0.10、输出 $0.50，按 [DeepSeek 峰值价](https://api-docs.deepseek.com/quick_start/pricing/) `deepseek-flash` 每百万输入 $0.30、输出 $1.20，三次各自最大费用及计数请求在发送前合计预留；超过 $0.60 即停止。这个余量是保守估算，不是服务商保证。对超时、断线和无 usage 的每次请求，按该次预留上限报告可能费用，不把它计为零；实际用量超过预留则报告异常，不自动重发。
