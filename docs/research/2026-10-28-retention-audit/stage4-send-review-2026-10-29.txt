**The runner has serious problems and is not ready to send the experiment.** For example, a response can contain invalid JSON yet be recorded as `completed: true`.

1. **Changed reservation counts can pass validation.** [verify_count](/Users/lchingen/hivemind-extraction-quality-2026-10-28/docs/research/2026-10-28-retention-audit/stage4-haiku-luna-v3-send-2026-10-29.py:75) checks the saved total but does not recompute each reservation from its token bounds and tariff. In a read-only, in-memory test, changing both bounds to `999999999` was accepted. The later usage check would trust those altered bounds, so it could continue scheduling even though the reservation no longer covers the reported usage.

2. **Missing output usage does not stop scheduling.** [unexpected](/Users/lchingen/hivemind-extraction-quality-2026-10-28/docs/research/2026-10-28-retention-audit/stage4-haiku-luna-v3-send-2026-10-29.py:105) treats a missing output-token field as zero. An in-memory response with input usage but no output usage was accepted as normal. That contradicts the frozen design’s rule to stop on missing usage while retaining the full reservation.

3. **A second worker can send the batch again.** [worker](/Users/lchingen/hivemind-extraction-quality-2026-10-28/docs/research/2026-10-28-retention-audit/stage4-haiku-luna-v3-send-2026-10-29.py:117) is directly callable and has no launch guard. A second worker can send up to eight requests before exclusive creation of existing result files fails. Those calls are outside the one-batch reservation, and their results may be lost. A crash after a request is sent but before its result is written also leaves no durable attempt record.

4. **Invalid answers can be labelled complete.** [one](/Users/lchingen/hivemind-extraction-quality-2026-10-28/docs/research/2026-10-28-retention-audit/stage4-haiku-luna-v3-send-2026-10-29.py:83) sets `completed` from the provider’s stop reason before checking JSON or structure. The in-memory test produced `completed: true` alongside `not JSON`. A natural stop is not enough to establish a usable answer; Anthropic also documents that an `end_turn` response can be empty. [Anthropic stop-reason documentation](https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons)

5. **A received response can be discarded during parsing.** If, for example, Luna returns an empty `choices` array, the exception handler saves only `IndexError`, discarding the already received response and usage. I reproduced this with an in-memory response. The same risk applies if later answer checks raise. This prevents the required record of the raw response and usage.

6. **The frozen request order is not protected against later changes.** The current ten request files are byte-for-byte identical to the reviewed v2 files, and the offline preparation verifier passed. But [the verifier](/Users/lchingen/hivemind-extraction-quality-2026-10-28/docs/research/2026-10-28-retention-audit/stage4-haiku-luna-v3-2026-10-29.py:215) compares reconstructed requests as Python dictionaries, where key order does not matter, and trusts hashes stored in the mutable manifest. Reordering the schema in both paired requests and updating those hashes can therefore pass while changing the schema order sent on the wire. Requests are also reread after verification, leaving a window for changes before dispatch.

On the normal path, the job list contains 30 distinct calls, with at most eight in flight, and the helpers make direct calls without a local answer cache or explicit retry. The saved reservation is **$0.4825293** against the $0.60 cap; it is an estimate, not a provider-enforced ceiling.
