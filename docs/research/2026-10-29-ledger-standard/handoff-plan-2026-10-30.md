## 3. 改动和测试的原则（每条的出处在 AGENTS）

1. 失败先诊断：数清这一类、追到产生它的那一句或那段代码、先问是不是测量造成的、用存的数据证明改动能翻过决定性的案例、报能去掉这一类的多少（§1）。
2. 发送之前先问模型自己：接着存下的对话问"哪一句让你这样判"，一分钱一次；模型的说法和请求指到同一处，才改（§1、§7.3）。
3. 提示词只带标准，不加新规则：每一句在标准页找得到出处；例子跨行业、不点名英伟达、不取测试文章；不靠加长，缺一句加一句、别处删同样多（§6，D237）。
4. 一次改一类、一处：改一句会改变每一次请求，所以量全部文章（§7.3）。
5. 每次付费发送之前写下：这次能改变什么决定、更便宜的检查漏了什么风险；只是在量噪声或已定的比较，就不发（§7.3，Alex："你跑这么多次真的有意义吗"）。
6. 分数是线索，trace 才是测量：每次都读漏掉的核心和辅助、一批多留的和抓到的（§7.2，D244）。
7. 尺子只数它被造来数的东西：质量结论还要读记录里的字段（原话人、日期、来源层、摘要的限定）和下游怎么用（§7.2，Alex："不要只是看尺子"）。
8. 读者或审查员报的问题是线索：每一处都对着原文或代码核过才记、才改（§1，Alex："验证是真的问题吗？"）。计数辅助（按词重合）只是线索，题有没有开要读候选问题原文。
9. 测试：每个测试写它证明哪条要求；先读被测的函数；只假装外部服务；在故意改坏的副本上测试必须失败、原代码上通过；不读密钥（§4）。
10. 验证到改动的那一层就停：存的数据能证明的不发；改代码用存下的决定确定性重放（$0）；全量只在最终配置上跑一次（§5）。
11. 跑的时候不改 `src/` 和提示词；看活库先拍快照；新数据新目录；只在被要求时提交（§9）。
12. 给 Alex 的话：第一行是答案，然后一个例子，再按他问的顺序；一句一个意思；不写一堆东西（AGENTS 授权一节）。

## 4. 量化准则

- 一把尺子：标准页 → 定稿金标 → §9.2 达标线。金标冻结后不改；后来发现的错单独记一份带日期的更正，分数注明用了哪一版（§7.1，D243 第 11 条）。
- §9.2 达标线（页上标的是提案，照抄要点）：核心每一次发送都 kept 且 correct，不带 material 记录问题；辅助三次里至少两次 kept；不收的模板 0/3；垃圾每篇不多于对照组中位数（基线，不是目标）；该开的题每次都提出且 settled_by 写得出，不该开的 0 次。分开报，不合成总分；分母为零写 not_exercised。
- 比较的做法（D245、D246 的验收就是这样做的）：新旧两版**同时**发（同一时段，防止服务端漂移），开发 118 + 测试 30，三遍；`final_scores.py PREFIX v旧 v新` 出每篇的数和配对 bootstrap 区间（文章为单位，种子 20261030）；回归先报；核心、辅助分开；区间跨 0 就说"在正常波动内"。
- 回归信号：别的版本都抓到、只有这一版丢的核心或辅助，读原始答案、问模型理由，追到是不是这次改的那句。注意：`loop-2026-10-29/surprise.py` 读的是旧参考（reference v2），不是现在的金标；按签字金标用 `per-article-<PREFIX>-dev.json` 里每篇每遍的命中算，脚本还没写，下一轮做全量之前先写好。
- 测试集每个配置只打一次分，不在上面调（D244）。
- 字段质量：没写过改动的读者盲读，再由我逐条对原文核实每一处标记（verdict 分 real / real_low / event / not_real / debatable，规则写在 `quality-2026-10-30/adjudication.py` 开头）；报核实后的数，读者的原始数放旁边。
- 成本从 token 按公开价算（`hivemind.model.PRICES`，gpt-6-luna $0.10/$0.50 每百万），不用存的 cost_usd（§7.2）。
