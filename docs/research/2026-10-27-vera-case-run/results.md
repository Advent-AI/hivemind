# Vera 单例结果：路由改善，整合没有贯通

实跑说明上一版设计只解决部分问题，不能把“先 Jev、再整理”当成完整答案。

例子：NVIDIA 给出 Vera 在特定 agentic 工作负载上的内部性能估算。这能为 CPU 竞争力提供线索，但本身不是新增收入，更不是第三方验证。合理处理应把这份新测试及其限制补进已有 CPU 研究，而不是自动另开一张 Vera 收入卡。

## 实际跑了什么

固定 D341 的源文 `gnews:caf5e64df9edf2e567ad2813`、已通过抽取的 e1、seq 1085 前的数据库。旧流程逐字重发 4391、4392、4393；新流程先让 Jev 比较来源与已有问题/证据，再让 Luna 读取这些原文及分数，决定增量与去向。每路三次，不投票、不挑答案，共 15 次成功 HTTP 调用。使用原有 Jev 1.14.0 与 gpt-6-luna low。

旧流程的决策用 v29 运行所在 worktree 的实际 `jev_matching` 代码重建；两路均经过实际 `matching.check` 与 `writing.write`，写入独立历史副本。原数据库只读。随后用实际 `judging.build_prompt` 构造下一步的输入，检查它究竟读到什么。

这次没有重跑抽取，也没有重跑最终判断模型。42 个旧问题与 10 条旧证据沿用保存的比较集合；未检验召回能力。原先 e2 的引用拒收、来源和日期问题仍在。新增问题分支只会记录未完成，没有伪造完整入库合同。

## 全部样本

| 样本 | 旧流程实际写入 | 新流程实际写入 | 旧 / 新 Jev 将 e652 判重复的概率 |
|---|---|---|---|
| 1 | 新建 v50；e1 合入 e652 | 更新 v5；保存新来源 e1484；不新建卡 | 0.52 / 0.55 |
| 2 | 新建 v50；e1 合入 e652 | 更新 v5；保存新来源 e1484；不新建卡 | 0.53 / 0.57 |
| 3 | 新建 v50；e1 合入 e652 | 更新 v5；保存新来源 e1484；不新建卡 | 0.54 / 0.55 |

每行都是新的独立副本，所以重复出现 e1484/v50 不代表重复写入同一个库。

三个新路样本均保留原 e1 的引用、摘要、说话人、证据类别及 event_time；其中摘要保留内部估算、AMD Venice、每核表现和四类工作负载。旧路只给旧 e652 增加来源引用，当前摘要仍是五月那条 1.5 倍每核、2 倍能效、4 倍密度的陈述，丢失新测试的区别。不是原始 HTTP 档案消失，而是后续研究读不到新的摘要。

## 哪些有效，哪些未成立

**观察到有效的部分：**三个新路答案都把性能线索放回现有 CPU 销售问题，不再用“Vera 范围更窄”自动创造收入问题。三个答案都区分了性能线索与实际销量/收入，也说明公司自己的测试不是独立佐证。

**不能归功于顺序：**新路同时改了问题单位、比较任务和分析者输入，不是只把旧 prompt 一分为二。Jev 在新路仍三次把新测试判成旧陈述。后面的 Luna 读新旧原文后没有执行这个合并意见。因此本实验不证明 Jev 必须在先，也没证明没有 Jev 会更差。

**整合没有进入下游：**三个新路副本中，v5 都有 96 条现行证据，其中同时有旧 e652 与新 e1484。实际下一步 prompt 包含新测试摘要，但不包含模型生成的 `research_update` 或 `qualifications`。原有 writer 只保存来源证据和链接；原有 reader 只读它们和之前的判断。新增字段没有消费者。这个结果证明保留增量，却没有证明避免重复计权或完成研究论据的合并。不能把 96 条都称为错误或重复，它们尚未逐条审查。

**一次语义错误：**第三次 `qualifications[1]` 说摘录没有列明具体工作负载，但 quote 已列 compiler、static analysis、Python benchmarks。四类未全部列出，不等于一类也未列出。这是 3 份新路答案中发现的 1 份错误说明；不能仅因目标 ID 正确就判为语义通过。前两份提到 quote 未点名 AMD Venice，确实如此：这个名称来自现有摘要；它们没有验证完整来源是否支持摘要。

上述语义检查由本助手阅读，非独立人工金标。单个已知失败开发案例的结果不是总体准确率。

## 需要修正的设计位置

当前缺口不是再增加一次判重，而是整理结果如何成为后续判断真正使用的研究记录。来源保留用于追溯；同一业务论据的新旧信息、增量、限制和支持方向需要被合并呈现，不能只返回几个目标 ID 后继续平铺原始证据。

这需要明确 writer 写什么、reader 读什么，并验证同源重复不会增加独立支持、新测试条件不会被抹去。现行冻结产品合同未包含本次的整理字段，所以这是未闭合的设计，不在本轮直接改变生产库、问题身份或判断公式。新建问题分支、来源溯源和时间接口也仍未验收。

估计模型费用 **$0.012869216**；保守预算记账 **$0.145794 / $0.50**。15 个请求全部结束，没有未知费用、重试或遗留调用。价格估算采用已有记录费率，不等于供应商账单。

| 1 | 124,222 / 31,782 | 152,268 / 39,641 |

| 3 | 124,222 / 31,782 | 152,274 / 39,641 |

新路总输入更大，因为整理模型需要同时看到来源与旧证据；去掉了旧候选数字阶梯和 Jev 的研究组成员问题，但增加了完整分析输入。本次测量不能支持“拆开以后更便宜”的说法。三份新路请求变化来自各自实际 Jev 输出。

运行中本助手有两个付费前错误，均保留：第一次 preflight 指向错误来源库而报缺失 item；本机主分支的 preflight 与原 v29 worktree 版本也不同。改用正确来源副本和原运行 worktree 后，4,217 项、772 次拒收及其原因与前次日志一致，仅路径标签变化。最初 runner 有 Python 括号错误，零调用阶段已修正；没有通过付费重试调试这些问题。
