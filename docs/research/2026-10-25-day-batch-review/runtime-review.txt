Found one serious failure-handling bug.

- **[P2] Queued Jev requests still start after the batch fails.** In [jev_matching.py:127](/Users/lchingen/hivemind/src/hivemind/views/jev_matching.py:127), `_answers()` submits every job upfront. If `future.result()` raises, the executor’s context manager waits for **all submitted work**, without cancelling queued futures. With two workers and twenty requests, failure of the first request can still cause the remaining queued requests to run before the item reports failure. This violates D172’s rule to cancel pending work and drain only requests already running, and can substantially delay stopping the day. Cancel pending futures on failure before waiting for running calls. The existing partial-failure test uses two jobs with two workers, so it cannot catch this queued-work case.
