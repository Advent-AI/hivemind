## 一句话

上游不断把已经贴好类别的信息推进来；系统把每条信息交给程序或模型读成事实，存进研究库，再由新事实推动研究结论更新。

## 为什么重建

旧系统是按日期主动去拉数据、一批一批处理的。同一件事的规则散在很多地方：信息的类型在 9 个模块里各有一套定义，配置有五层覆盖，时间有好几套时钟。结果是问“某类信息进来会怎样”，要读好几处代码才说得清。新系统从头设计，每件事只在一个地方决定。

## 系统的边界

- **上游（不归本系统）**：取得材料、按分类规则贴好类别，推送进来。以后再谈。
- **本系统**：从“分发”开始，到研究库和研究结论。
- **测试**：用一个测试程序，把测试库里的旧数据按发布日顺序推进来，走和正式运行完全相同的路。

信息走的路：

```
上游（取得材料 + 分类）→ 分发 → 代码处理（表格）或 模型抽取（文字）→ 研究库 → 研究结论
```

旁边的几条线：

| 从 | 到 | 是什么 |
|---|---|---|
| 研究对象名单 | 上游 | 推哪些对象的哪几类信息 |
| Config | 分发 → 模型抽取 | 模型读文字时的设置 |
| 分发、模型抽取 | 人工复核池 | 查不到、有问题的东西 |
| Pull 模式 | 研究结论 | 到期或定时，主动去查证 |

## 两种工作方式

| | 信息流（现在设计） | Pull 模式（以后设计） |
|---|---|---|
| 谁触发 | 有信息推进来 | 到了约定日期，或按固定时间 |
| 谁主动 | 上游推，系统接着处理 | 系统主动去查 |
| 做什么 | 把信息读成事实，推动相关结论更新 | 查某个结论的条件满足了没有 |
| 看不看日历 | 从不看 | 系统里唯一按时间触发的地方 |

## 基本原则

1. **由信息推动，不由日历推动。** 没有新信息进来，系统什么都不做；结论的每一步更新，都来自一条真实的信息。
2. **时间只看发布日。** 每条信息按纽约时间算是哪天发布的，几点几分不参与任何判断；系统里没有“今天是哪天”的概念。
3. **只有研究对象名单决定处理什么。** 名单写明研究哪些对象、每样看哪几类信息；上游只推这个范围，推进来的都处理；分发不看信息讲的是谁。
4. **程序读还是模型读，由形式决定。** 表格给程序，文字给模型，不需要人来选。
5. **查不到的不猜。** 对照表里没有、规则判断不了的，放进人工复核池等人看。
6. **不存原材料。** 原材料留在上游的库里；系统只存处理记录和读出来的事实。
7. **改动留痕。** 名单、Config、对照表改一次就是一个新版本，旧版本留着。

## 和旧系统的区别

| | 旧系统 | 新系统 |
|---|---|---|
| 数据怎么进来 | 按日期主动去拉 | 上游推进来，来了就处理 |
| 怎么处理 | 一批一批跑，按天推进 | 一条一条处理，由信息推动 |
| 信息类型 | 9 个模块各自定义 | 16 个类别，一份规则 |
| 处理什么 | 配置、命令参数、多个 preset 层层覆盖 | 只有研究对象名单决定 |
| 时间 | 好几套时钟 | 只看发布日 |
| 原材料 | 自己存一份 | 不存，留在上游 |

## 还没设计的

研究库里的事实长什么样；研究结论（thesis、ladder、evidence）；Pull 模式；人工复核池的处理流程；上游怎样取得材料和分类；模型设置是共用一套还是每类一套。
